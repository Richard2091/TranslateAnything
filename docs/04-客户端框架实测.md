# 04 · 各客户端框架沉浸式翻译实测（2026-11-28）

目的：找出 Electron / WebView 系以外各种客户端框架"读出界面文字"和"原地改写"的最佳方式，为沉浸模式后续通道定顺序。测试机 Windows 10 19045 x64，全部在普通权限下进行。原型代码留在本机 `lab/` 目录（已加入 `.git/info/exclude`，不入库）。下面记录可复现的关键做法。

## 结论速览

| 框架 | 最佳方式 | 实测结果 | 兜底 |
|---|---|---|---|
| Electron / CEF / WebView2 | CDP（已实现） | ✅ | — |
| WinForms / WPF（.NET Core 3+ / .NET 5+） | **.NET 启动钩子**原地改写 | ✅ 全部生效，WPF 布局自动适应 | UIA 贴译文 |
| WinForms / WPF（.NET Framework） | 运行时注入（参照 Snoop） | 未测 | UIA 贴译文 |
| UWP / WinUI 3 | **XAML 诊断接口**原地改写 | ⚠️ 固定文字成功；绑定文字被写坏，修法已明确，待验证 | UIA 贴译文 |
| Qt（动态链接、标准 Qt） | **hook `QCoreApplication::translate`**，`setText` 一类函数兜底 | ✅ 新对话框全部生效；主菜单栏要靠兜底 | UIA 贴译文 |
| Win32 / MFC 标准控件、菜单 | **外部 `WM_SETTEXT` + 改菜单**，不注入 | ✅ | UIA 贴译文 |
| WPS（改名版 Qt、自绘控件） | **语言包**（替换 `.qm`） | 格式已确认可改；替换效果未实测（要管理员权限） | 悬浮窗 OCR |
| Flutter | UIA 贴译文 | ✅ 读得全、坐标准 | 悬浮窗 OCR |
| Windows Ribbon（写字板等）、静态链接 Qt | UIA 贴译文 | ✅ | 悬浮窗 OCR |
| Java（Swing / JavaFX） | 未测（本机没有 JDK） | — | — |
| DuiLib 等自绘界面、游戏 | 悬浮窗 OCR | — | — |

## 一、读取：系统无障碍接口（UIA）

做法：原生 COM `IUIAutomation` + `CacheRequest`（`TreeScope_Subtree`、控件视图、`AutomationElementMode_None`），一次取回整棵树的文字、类型、坐标、框架标识。

| 框架 | 实测程序 | 读到的文字 | 取树耗时 |
|---|---|---|---|
| Win32 | 记事本 | 菜单、状态栏、标题全有 | 19 ms |
| MFC + Windows Ribbon | 写字板 | 功能区按钮、分组、标签页全有 | 87 ms |
| WinForms | 自写 demo | 除自绘面板外全有（菜单、工具栏、标签页、列表、树、表格） | 54 ms |
| WPF | 自写 demo | 全有，含换行段落、富文本 | 70 ms |
| UWP | 计算器 | 全有 | 27 ms |
| WinUI 3 | WSL 设置 | 全有 | 24 ms |
| Qt5 标准控件 | yuzu | 菜单、表头、列表、状态栏都有 | 24 ms |
| Qt5 自绘控件 | WPS | 首页只有 6 处，编辑界面功能区一个字都没有 | 130 ms |
| Flutter | RustDesk、LocalSend | 正文、按钮、标签都有；图标按钮没有文字 | 18–22 ms |

- **必须用原生接口**：.NET 自带的托管客户端（`System.Windows.Automation`）读 WinForms 会漏掉菜单和工具栏，读写字板要 14 秒。
- 坐标是物理像素，与截图一致。
- 要过滤的噪声：WinForms 容器控件的 Name 会继承相邻标签的文字；WPF 按钮里还嵌着一层同样的 Text；滚动条、标题栏按钮等系统元素。
- 方案原先写的"Qt 需程序开启无障碍"不准确：Windows 上标准 Qt 控件直接可读，读不到的是自绘控件（如 WPS）。

## 二、原地改写

### 1. 不注入、从外部改（Win32 / MFC）
- 子窗口文字：`SendMessageTimeoutW(WM_SETTEXT)` 跨进程可用，系统负责搬运字符串。
- 菜单栏：`GetMenu` + `SetMenuItemInfoW(MIIM_STRING)` + `DrawMenuBar` 跨进程可用（记事本实测）。
- **WinForms 不适用**：只有一部分生效，标签不自动变宽、按钮重绘异常、复选框不变，菜单、工具栏、标签页、列表都改不动——WinForms 按自己缓存的 Text 绘制。
- Windows Ribbon 不是窗口控件，改不动；WPF、Qt、UWP 没有子窗口，这条路不适用。
- 输入框（类名含 Edit）里是用户数据，不改。

### 2. .NET 启动钩子（WinForms / WPF）
- 做法：启动目标程序时带环境变量 `DOTNET_STARTUP_HOOKS=<钩子 dll>`，运行时在 `Main` 之前调用钩子里无命名空间的 `StartupHook.Initialize()`。和 WebView2 现在"带环境变量重启"的流程一致：只设在随译拉起的进程上，不写系统、不改文件。
- WinForms：在界面线程上遍历 `Controls`、`ToolStrip` 项、`ListView` 列与项、`TreeView` 节点、`DataGridView` 列头，改 `Text`；新窗体靠 `Application.OpenForms`。实测菜单、工具栏、标签页、列表、树、表头、状态栏、窗口标题全部生效，自动大小的标签跟着变宽；固定宽度的按钮会截断。
- WPF：`EventManager.RegisterClassHandler(typeof(FrameworkElement), LoadedEvent, …)` 注册全局 Loaded 事件，此后新出现的元素都会经过；改 `TextBlock.Text`、`ContentControl.Content`（字符串）、`Header`、窗口标题。实测全部生效，按钮变宽、段落重新换行。
- **绑定来的文字不改**：`BindingOperations.IsDataBound` 为真的跳过，否则会切断数据绑定；实测数据单元格保持原样。
- 富文本（句中夹粗体）要整段翻译、保留格式占位，不能逐个 Run 翻。
- 限制：只适用于 .NET Core 3.0+ / .NET 5+；剪裁或 NativeAOT 发布的程序可能关掉了启动钩子；.NET Framework 程序要改用运行时注入。
- 教训：第一版在遍历时修改集合，**直接把目标程序弄崩**。进程内代码必须全程兜住异常。

### 3. XAML 诊断接口（UWP / WinUI 3）
- 做法：
  1. `CreateRemoteThread(LoadLibraryW)` 把 TAP DLL 注入目标进程；
  2. TAP 在目标进程内、用自身 pid 调 `InitializeXamlDiagnosticsEx`——从外部跨进程调用一直返回 `0x80070490`，走不通；
  3. 框架回调 `DllGetClassObject` → `IClassFactory` → `IObjectWithSite::SetSite`，拿到 `IXamlDiagnostics`，再取 `IVisualTreeService2`；
  4. **另开线程**调 `AdviseVisualTreeChange` 订阅可视树（在界面线程上调会死锁）；
  5. 改 TextBlock：用 `GetPropertyValuesChain` 里 Text 项的索引（`GetPropertyIndex("Text")` 会返回 `E_INVALIDARG`），`CreateInstance("Windows.Foundation.String", 新文字)`，再 `SetProperty`。
- 端点名要带编号循环探测，直到不再返回 `ERROR_NOT_FOUND`：UWP 用 `VisualDiagConnection<N>`，WinUI 3 用 `WinUIVisualDiagConnection<N>`。
- 导出位置：UWP 在系统 `Windows.UI.Xaml.dll`，WinUI 3 在 `Microsoft.Internal.FrameworkUdk.dll`。
- UWP 跑在 AppContainer 里，TAP 文件要授权 `icacls <dll> /grant *S-1-15-2-1:(RX)`；注入本身不需要管理员。
- 实测：计算器、WSL 设置都没崩，Defender 没拦；写死在界面里的文字改写成功，布局自动适应，新元素经订阅自动处理。
- 待解决：
  - **绑定文字被写坏**：计算器按键、WSL 设置的列表变成一串数字（原型把值的句柄当原文写回去了），图标字体变方框。要先用 `GetIInspectableFromHandle` 取真实字符串、跳过图标字体，未验证；
  - 程序自己更新文字时不触发回调，译文会被原值覆盖，要另外跟踪属性变化；
  - TAP 目前卸载不了，还原只能重启目标程序。
- **WPF 不适用**：WPF 进程里没有这套接口，走 .NET 启动钩子。

### 4. Qt hook（yuzu，Qt 5.15 x64）
- 做法：
  1. `SetWindowsHookEx(WH_GETMESSAGE, …, 目标界面线程)` 把 DLL 加载进目标，初始化在界面线程上做；
  2. detour `QCoreApplication::translate`（MSVC x64 修饰名 `?translate@QCoreApplication@@SA?AVQString@@PEBD00H@Z`，返回值走隐藏指针）；
  3. 手动给 qApp 发 `QEvent(LanguageChange)`，触发程序自己 retranslate。
- 读写 QString 全部调用目标自己的 Qt 导出函数（`fromUtf16`、`utf16`、`size`、`operator=`、析构），不依赖内存布局。
- 实测：新打开的对话框全部生效（构造时每个 `tr()` 都经过 hook）；已打开界面的表头、搜索框等刷新了；**主菜单栏没刷新**，因为 yuzu 收到 LanguageChange 时没重跑主窗口的 retranslateUi。覆盖面取决于目标程序自己是否 retranslate，要用 detour `QLabel / QAbstractButton / QAction::setText`、`QWidget::setWindowTitle`，再遍历现有控件兜底（已验证可用）。
- 坑：
  - "装一个空 QTranslator 触发刷新"不成立，Qt 对空翻译器不广播，必须手动发事件；
  - DLL 卸载前不还原 detour 会让目标崩溃，在 `DLL_PROCESS_DETACH` 里先还原后，多轮注入、卸载都正常；
  - 富文本（HTML）加前缀后被破坏成原始 HTML，要识别富文本、只翻标签内的文字；
  - 同一段文字被处理两次会叠加，要做到重复处理不叠加。
- 本机杀软（火绒）没拦；纯内存修改，进程退出无残留。
- 推广性：
  - 32 / 64 位各一份 DLL；
  - MSVC / MinGW、Qt5 / Qt6、自定义命名空间各需一组符号名，运行时探测；
  - 静态链接 Qt 的程序没有导出可取，不走 hook。

### 5. WPS：语言包
- WPS 12（32 位）用改名版 Qt 5.12（`Qt5CoreKso.dll` 等，`QT_NAMESPACE=kso_qt`，符号名带 `kso_qt`），标准 Qt hook 不通用；它的自绘控件 UIA 也读不到。
- 界面原文是英文，中文来自 `office6\mui\zh_CN\*.qm`：18 个文件约 6.8 万条；`mui\en_US` 只有配置文件。
- 这些 `.qm` 只存"原文哈希 + 译文"，不带原文和上下文。但 Qt 按哈希查表，**保留哈希、只替换译文就能生成其他语言的包**（把中文译成目标语言）；切回英文就是 WPS 的原生界面。
- 写安装目录需要管理员权限；替换后的效果、WPS 是否校验这些文件，都还没实测。

## 三、共性问题（各条进程内通道都要处理）

- 绑定来的数据文字不改（WPF 绑定、XAML 绑定、表格单元格）。
- 富文本整段翻译、保留格式占位。
- 同一段文字重复处理不叠加：记住哪些是我们写进去的。
- 程序自己更新文字时要跟上，否则译文被原文覆盖。
- 进程内代码全程兜住异常，卸载前先还原 hook。
- 固定宽度控件放不下译文：接受截断，或在控件上缩小字号（待定）。
- hook 函数里不能同步等网络：缓存命中当场替换，未命中先显示原文，异步翻译后回填。

## 四、通道顺序（2026-11-28 用户拍板，按此推进）

1. **UIA 贴译文**：不注入，一次覆盖除自绘以外的几乎所有原生框架，也是各条原地改写通道失败时的兜底。
2. **.NET 启动钩子**：最简单、最稳，复用现有"带环境变量重启"的流程。
3. **Win32 外部改写**：工作量小，作为 Win32 / MFC 程序 UIA 之上的增强。
4. **Qt hook**：子任务估计 x64 标准 Qt 可用原型 1.5–2 周，产品级再加 4–6 周。
5. **XAML 诊断接口**：子任务估计 2–3.5 周，要先解决绑定文字。
6. **语言包模式首个目标定为 WPS**：先实测 `.qm` 替换。
