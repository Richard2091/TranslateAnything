# 02 · 技术方案

## 技术栈

- **Tauri 2 + Rust**（stable-msvc 工具链），前端用 **Vite + 原生 TS**（界面极简，不引 React/Vue 这类框架；若设置页变复杂再说）。
- 包管理：pnpm。

## 单实例启动（Windows）

- 在初始化 Tauri 之前，用 `single_instance.rs` 获取当前登录会话的命名互斥量。锁名固定，安装版、便携版和不同目录的副本共用同一把锁。
- 只有取得所有权的主进程才读取配置、创建托盘和注册快捷键。重复启动时新进程直接退出。退出或崩溃后，Windows 释放锁，允许重新启动。

## 窗口方案

1. **框选遮罩 overlay**：覆盖光标所在显示器，背景 1/255 透明度（不置灰，但能接收鼠标），只画选区边框；框选完成后销毁，把选区（物理像素）交给后端。
2. **翻译框 frame-N**（`live.rs`）：无边框、透明、置顶、不抢焦点，并且：
   - 实时截屏不截屏幕，而是截翻译框**下面的窗口**（`capture::capture_under`）：按 Z 序找出与框相交的其他程序窗口（跳过本进程、隐藏/cloaked、鼠标穿透的悬浮层），直到遇到完全盖住框的那个，再从下往上逐个 `PrintWindow(PW_RENDERFULLCONTENT)` 拼成框内画面。这样截到的始终是原始内容，不会把译文截进去，也不用隐藏窗口，不会闪烁；全屏 1920×1080 窗口约 26ms。
   - 弃用方案：`SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` 会让透明的 WebView2 窗口在屏幕上也不可见（2026-11-16 真机确认），不要再用。
   - 已知限制：不支持 `PrintWindow` 的程序（少数游戏、硬件加速视频）截到的可能是黑屏；只盖住一部分的半透明分层窗口会被忽略。
   - **WGC 截取**（2026-11-18，`wgc.rs`，由 `capture::Capturer` 选择）：框下只有一个窗口时改用 Windows.Graphics.Capture 按窗口截取——DWM 合成好的 GPU 纹理直接交过来，只回读框内区域；窗口内容变化才来新帧（`FrameArrived` 立即唤醒跟踪循环），每帧带合成时刻。按窗口截取不受遮挡，天然不含翻译框。帧画面原点是窗口可见边界（`DWMWA_EXTENDED_FRAME_BOUNDS`），与 `PrintWindow` 逐像素一致（真机核对）。
     - 实测（1110×435 区域，150% 缩放，开发构建）：WGC 截屏约 6ms、画面平均只晚 2ms、约 100 帧/秒；`PrintWindow` 约 55ms、17 帧/秒。
     - 限制：**Windows 10 上被截窗口会出现系统强制的黄色边框**，Windows 11 才能关（`IsBorderRequired`），所以默认只在能关边框的系统上启用，其余仍用 `PrintWindow`；关边框失败也自动退回。框下有多个窗口（菜单、弹窗盖进来）时这一帧用 `PrintWindow`，WGC 会话保留。首次建立会话约 0.3s。
     - 调试：环境变量 `TA_CAPTURE=wgc` / `printwindow` 强制截屏方式（Win10 强制 WGC 会有黄框）。
3. **设置窗 settings**（M3）：普通窗口，从托盘菜单打开。

### 翻译框鼠标操作

- **默认与当前状态**。设置页的「框内鼠标操作」通过 `settings_save` 保存顶层 `frame_click_through`。打开新框时读取该值并初始化该窗口的鼠标模式。旧配置缺省为 `true`（鼠标穿透），`false` 为框内拖动。设置保存后，新开的框立即采用新默认值，已打开的框继续使用各自的模式。
- **单框命令**。`frame_get_click_through()` 读取调用窗口的当前模式。`frame_set_click_through({ clickThrough: boolean })` 切换调用窗口的模式。两者成功时返回当前布尔值，单框更改只保存在内存中。悬停循环在下一个 40ms 检查周期应用命中变化，左键按住时等到松开再更新。暂停和原文/译文显示状态独立于鼠标模式。
- **命中区域**。鼠标穿透模式只在正文区域忽略鼠标。`live.rs` 的悬停判断让边缘和工具条接收鼠标，并在拖拽期间保持交互。框内拖动模式由翻译框接收框内点击和滚轮，正文左键调用 `startDragging`。两种模式都可在边缘调用 `startResizeDragging`，也可用工具条手柄移动。工具条按钮拥有独立命中区域，按下按钮只执行各自的操作。边缘和工具条的 CSS 尺寸要按窗口当前缩放系数转换为物理像素，与前端布局一致。
- **显示与反馈**。鼠标模式用指针/手形图标和框内玻璃效果区分。玻璃层位于译文下方，在边框内侧留出间隔。方向性反光和内缘阴影模拟玻璃厚度，中央保留透视，切换时仅过渡透明度。切换鼠标模式时边框颜色、线宽及圆角一致。工具条悬停提示说明点击后切到哪个模式，切换成功后短暂显示当前模式。模式按钮的无障碍名称保持固定，用 `aria-pressed` 表示是否启用穿透。窄框优先保留手柄、模式切换和关闭。模式样式使用短过渡，尊重 `prefers-reduced-motion`。
- **全局圆角**。`frame_corner_radius` 使用 CSS 像素，默认 `0`（直角）。设置输入框接受 0–128 的整数，有效输入通过 `frame-corner-radius-preview` 同步预览。回车或失焦后保存，`settings_save` 保存成功后广播 `frame-corner-radius`。预览结束或设置窗口销毁时清除临时值。框选遮罩和翻译框复用圆角初始化逻辑，先订阅变化，再通过 `frame_get_corner_radius()` 读取持久化值。CSS 按选区或框体尺寸约束实际圆角。边角缩放热区保留矩形尺寸，圆角设置不触发几何变化或重新翻译。

### 鼠标模式性能验证（Windows）

- 两种模式共用截屏、OCR 和翻译链路。拖动期间根据最近一次几何变化暂缓截屏，停止约 90ms 后重新读取窗口位置。未参与预测的滚轮不会推迟截屏计时。
- 本地 Debug 用独立便携实例覆盖 WinForms 测试窗口，使用英语 OCR 和精确术语表命中。每个模式执行一次从 310×160 到 330×176 的程序化移动与缩放，再回到原区域。最后一次 `SetWindowPos` 到后端记录译文就绪，穿透为 164.5 / 175.6ms，拖动为 156.7 / 144.2ms。用例没有外部引擎请求。计时包含几何停稳等待，截止于后端日志，不包含 WebView2 绘制。该次冒烟用例未测量实际鼠标手势或持续拖动帧率。

## 数据流（实时循环，每个翻译框一个）

```
跟踪（画面变化时尽快截，PrintWindow 约 30 帧/秒、WGC 约 100 帧/秒；静止 0.8s 后降到每 100ms 一次；
      正文区域有穿透的滚轮、按下翻页键或 WGC 来新帧时立即醒来，不等空闲间隔）：
  截取框内画面（WGC 或 PrintWindow 截下层窗口，不含翻译框自身）
  └─ 框移动/缩放或 DPI 变化 → 前端清空旧译文，合并本帧的边框尺寸更新
     └─ 原生事件更新时间戳，停稳约 90ms 后读取新几何、epoch + 1，清零累计滚动量并重新识别
  └─ 与上一帧比较，变化像素 < 0.2% → 跳过；滚动后画面静止 ≥30ms → 补发一次不变的 total（前端据此立刻停止外推）
  └─ 估算整体滚动位移（行/列签名匹配：抽样粗搜 + 候选附近精搜）→ total += 位移
       → 立即 emit("shift", {epoch, total, age, sent})，前端平移现有译文（不等 OCR）
  └─ 若没有 OCR 在跑：把这一帧交给后台 OCR，记下 base = 当前 total

后台 OCR（同一时刻只跑一个，总是识别最新画面）：
  OCR（含每个单词坐标）→ layout.rs 识别标题与列表、按大间距拆栏、归并段落块
  └─ 取样背景色（外框中位数）与文字色（笔画核心像素，避开抗锯齿浅边）
  └─ 估算原文样式：字号（按单词字母组成换算框高）、行距、字重（笔画宽度/字号）、对齐
  └─ 结果交回跟踪循环

跟踪循环取到 OCR 结果 / 译文到达：
  └─ 段落原文查缓存：命中直接用；未命中的批量请求翻译（同一时刻只有一个请求在途，失败 3s 后重试）
  └─ emit("layout", {epoch, base, total, blocks}) → 前端按原位置画色块 + 译文，
       整层平移 total - base（补偿 OCR 期间发生的滚动）
```

滚轮预测（`input.rs` + 前端 `scroll.ts`）：
- 后端用 Raw Input（只读）接收全局鼠标滚轮。只对穿透模式下落在正文、由下方应用接收的滚轮唤醒跟踪循环并发送 `wheel` 事件，供前端预测。翻译框接收的滚轮应跳过预测，避免下方画面未动时译文产生假位移。实际画面变化仍走常规跟踪。
  翻页键（PgUp/PgDn/方向上下/空格/Home/End）由悬停循环顺带轮询这几个键的状态，不监听全局键盘。
- tao 启动时会为自己注册鼠标/键盘 Raw Input（只用于 Tauri 不转发的 DeviceEvent）；同一进程每类设备只有最后一次注册生效，
  我们之后注册鼠标会接管鼠标这一类，不影响现有功能。
- 前端每次滚动结束时用「实测总位移 / 滚轮格数」学习每格像素数、用单格滚动到达 90% 位移的时刻学习滑动时长
  （shift 消息带 age = 这帧画面截于多少毫秒前，按真实截屏时刻计算）。连续两次吻合后开始预测：
  滚轮一动，译文按缓出曲线 1-(1-t)³ 立即滑向「起点 + 每格像素 × 格数」，同时取预测与实测中走得更远的那个。
- 保护：实测确认界面开始移动前，预测最多领先 max(24px, 0.6 格)；滚轮后 110ms 界面没动视为到底，取消预测并暂停该方向；
  精确式触控板（非 120 整数倍的增量）直接跟手平移、没有滑动动画，只唤醒、不预测不学习。
- 滚到头：动了一段又停在预测目标之前（预测动画本该还在进行，实测却停了），也立即取消预测并暂停该方向。

滚动跟随（前端 `scroll.ts`，2026-11-18 重写；滚轮预测是其中一部分）：
- **时刻还原**：shift 带 age（截屏到发出）和 sent（发出时刻，Unix 毫秒），页面用 `Date.now() - sent` 再扣掉事件传递时间，
  得到每次实测对应的真实截屏时刻。
- **速度外推**（取代原来 22ms 时间常数的指数平滑追赶——那本身就多晚 20ms 以上）：在 ≥30ms（且不短于两个实测间隔）的时间窗内测速，
  与前一个时间窗比较，减速时估出衰减时间常数；把译文推到"上屏那一刻"内容应在的位置（实测 + 外推到 now + 32ms，
  透明 WebView 窗口从设定到上屏约两帧，实测得出），最多看 90ms。从静止起步的第一次实测只对齐不外推（分不清平滑滚动与无动画跳格）；
  收到位置不变的实测即视为停下；超过预计下一次实测的时刻仍无新实测，外推在 50ms 内收回。触控板、拖滚动条、翻页键都靠它跟随。
- **只进不退**：滚动途中目标往回缩（外推冲过头、估出在减速）时原地等内容追上，不往回拉；停下后再对齐实测。
- **淡出**：每次实测到达时，回查"截屏那一刻屏幕上译文的位置"（显示位置历史）与实测比较，得到真实错位；
  错位 5~20 CSS px 时译文层线性变淡到 20%，错位记录按 140ms 时间常数衰减，稳定后淡回。从静止起步的那次实测必然落后，不计。
- 模拟（`scroll.ts` 新旧对比，上屏延迟按 32ms，平均错位 px，旧 → 新）：
  PrintWindow（每 35ms、晚 30ms）：滚轮连滚 29 → 9、触控板惯性 52 → 16、拖滚动条急停 47 → 20；
  WGC（60 帧/秒、晚 6ms）：滚轮连滚 27 → 6、触控板惯性 36 → 9、拖滚动条急停 31 → 11；无动画跳格新旧持平（约 30~40）。

固定区域不漂移（2026-11-19）：
- 整体位移按全框估计，框里固定不动的部分（标题栏、侧栏、视频字幕、原地刷新的文字）以前也跟着整体平移，译文漂离原文，直到下一次 OCR 才回位；
  固定部分占比稍大时整体估计还会失败，滚动部分的译文又完全不跟随。
- 位移估计改用截尾平均（只取最吻合的六成行）：最多四成的行不随滚动时仍能估出位移。
- 逐块核对（`motion::classify_region`）：每次估出位移后，比较各块原位置的画面在"原地"与"平移后"哪个更吻合，
  原地没动的块钉在屏幕坐标上（`live::Anchor`），前端放进不随滚动平移、不淡出的 `#pinned` 图层；钉住的块之后又跟着动了就放回滚动层。
  OCR 结果到达时，若识别期间发生过滚动，用识别那一帧与最新画面对比做同样的判断；上一版钉住、同位置同文字的块继续钉住。
- 真机（Edge 测试页脚本滚动，CDP 同时记录页面滚动与译文层位置，换算到同一系统时钟；中间版本，测速时间窗等最后一轮调整未复测）：
  译文落后页面的时间 旧 + PrintWindow 68ms → 新 + PrintWindow 16ms；旧 + WGC 40ms → 新 + WGC 约 20ms；
  计入淡出后的平均错位 15 → 4~5 CSS px。外推带来的抖动 PrintWindow 下约 9px、WGC 下约 3px。
- 注意：不同浏览器进程的 `performance.timeOrigin` 与系统时钟可差近 100ms，跨进程比较时刻要先各自换算到 `Date.now()`。

原文样式还原（`layout.rs`）：
- **字号**：OCR 单词框高取决于字母组成——只有 x 高度的词（mean）≈ 0.52em，含大写/升部（The）≈ 0.73em，
  只有降部（gap）≈ 0.72em，上下都伸出（lightly）≈ 0.93em，中日文 ≈ 0.88em。逐词换算后取中位数，译文用同样的 em 字号。
- **行距**：多行段落取相邻行顶部间距中位数，译文 line-height 与之相同，首行行框中心对齐原文首行；单行块让译文在块内垂直居中。
  放不下时先把行距收紧到 1.2 倍，再逐步缩小字号。
- **字重**：按覆盖度累加算出亚像素级笔画宽度，笔画宽度 / 字号：常规 ≈ 0.08~0.09、半粗 ≈ 0.11、粗体 ≈ 0.15~0.17；
  深底浅字同字重的比例约为浅底的 1.25 倍，先折算。
- **对齐**：多行看各行左边缘是否参差而中心对齐；单行看两侧到边框的留白是否对称（按钮、标签）。
- **组件边界**：相邻两行只有在行高相近、估算字号之比在 0.85~1.18、文字色差 ≤ 80（RGB 各通道差之和）、水平有重叠、
  垂直间距小时才合成一段。邻近正文更宽、笔画明显更细时，短标题独立成块。
- **列表**：项目符号和短编号各自起块，换行续文按正文缩进和行距归入同一项。OCR 漏掉实心圆点时，以行首左侧独立的圆点像素补回。
  首项只识别出句点时，结合后续连续编号、对齐和残留笔画补回 `1.`。标记与正文两列渲染，保留悬挂缩进。只有正文参与翻译和缓存。
- 色块按原文所占范围外扩 0.18 行高（2~5px）完整盖住原文，译文在同样的宽高内排版：短了留白，长了先收紧行距再缩字号。
- 校准方法：`layout::tests::字号校准`（ignored）可读取截图或抓取后台窗口，打印每段估算值。

- 缓存键是段落原文，所以滚动、缩放后同一段文字不会重复翻译，只有新进入框内的文字才会产生请求。
- 贴着上下边缘、被截断的行不参与翻译（识别不可靠），滚动进来完整后再翻。
- 目标语言为中文时跳过本身就是中日文的段落，纯数字/符号段落也不翻译（将统一到 `filter.rs`，见"翻译过滤"一节）。
- 实测（1000×700 区域）：OCR + 分段约 50ms，Edge 批量翻译约 0.5s。
- 实测（900×750 区域，release）：跟踪一帧约 35ms（截屏约 29ms），约 29 帧/秒；开发构建约 13 帧/秒（均为 PrintWindow）。
  `live::tests::跟踪帧率`（ignored）可测帧率与画面延迟，配合 `TA_CAPTURE` 对比两种截屏方式。
- 后台 OCR、翻译完成后立即唤醒跟踪循环推送结果（`FrameCtl::ready`），不等下一拍；空闲时一拍是 100ms，否则每轮白等约 0.1~0.15s。
- **耗时日志**（2026-11-18）：debug 构建在控制台输出以 `[耗时]` 开头的日志（`timing.rs` 的 `tlog!`，release 下编译期去掉）：
  悬浮窗每次 OCR 一行（截屏、灰度化、画面比对、OCR、分段）、每批翻译一行（术语表、译文库、引擎、写库）、
  每轮一行"画面变化 → 译文全部上屏"总耗时；沉浸模式每批一行（翻译、回填页面）；引擎失败回退时记下失败引擎的耗时。
  2026-11-18 实测（debug，约 1100×400 区域）：截屏约 53ms、OCR 15~50ms、分段 2~5ms，Edge 批量翻译 0.87~0.93s，
  一轮共 1.1~1.2s，其中约 0.15s 是等下一拍（已改为完成即唤醒）——**瓶颈在在线翻译请求**，这是引入离线翻译的动机。

坑位提醒：
- **DPI**：后端一律用物理像素；前端除以 `devicePixelRatio` 换成 CSS 像素。
- **OCR 坐标**：OCR 前图像可能被放大/缩小，单词坐标要除回缩放倍数。
- **OCR 语言**：`OcrEngine::TryCreateFromUserProfileLanguages` 优先；允许配置指定语言。

## 两种显示模式

| | 悬浮窗模式（`live.rs`） | 沉浸模式（`immersive/`） |
|---|---|---|
| 触发 | 快捷键框选区域 | 配置好目标应用后自动接管，`Alt+Shift+T` 切换译文/原文 |
| 取文字 | 截屏 + OCR | 直接读界面文字（DOM），不识别图像 |
| 显示 | 透明置顶窗口盖在原文上 | 应用自己用译文排版渲染，没有任何浮层 |
| 适用 | 任何程序（游戏、图片、视频字幕、自绘界面） | 已接入通道的程序（目前：Electron / Chromium 内核；后续通道见"沉浸模式"一节，各平台覆盖见"各平台覆盖范围"） |

两种模式共用翻译引擎链（`translate_batch_with_fallback`）和译文本地库，可以同时开启：沉浸模式接管得了的应用就原地改写，接管不了的照样框选用悬浮窗。另规划第三种"语言包模式"（直接翻译软件自带的语言文件，即"汉化"），见"语言包模式"一节。

## 译文本地库（`store.rs`）

- 位置 `~/.translate-anything/translations.db`，SQLite（WAL）。表 `translations`，主键（目标语言，原文），另存译文、引擎、命中次数、首次/最近使用时间，以及为设置界面"改译/词典"预留的 `manual` 标记（自动翻译不覆盖手工译文）。
- `translate_batch_with_fallback` 先批量查库，只把未命中的原文交给引擎，结果写回库；全部命中时返回的引擎名为"本地缓存"，不发任何网络请求。`persist_cache: false` 可关闭。
- 不区分引擎：换引擎后旧译文继续有效；想全部重翻就删掉这个文件。
- 译文与原文相同（产品名、专有名词）也入库，免得每次都去问引擎；空译文不入库。单条原文超过 4000 字不入库。
- 悬浮窗模式内存里的段落缓存仍保留，作为库前面的一层。

## 术语表（`translate::glossary`）

- 传统翻译引擎翻单个界面词没有上下文，实测 reclaude 客户端里 "New → 新款"、"Artifacts → 文物"、"Auto → 汽车"、"On-call → 随叫随到"。术语表按**整条原文精确匹配**（忽略首尾空白），命中的既不查库也不请求引擎，优先级：自定义 `glossary` > 内置术语表 > 译文库 > 引擎。
- 内置术语表 `translate/glossary.json` 按目标语言分组，收录常见界面词和 reclaude 客户端用到的词；`builtin_glossary: false` 可关闭。
- 自定义 `glossary` 写在配置里；译文写成与原文相同即"保持原样不翻"。后续设置界面的"改译"功能写到译文库的 `manual` 条目或这里。
- 沉浸模式注入页面时把术语表并入预加载，命中当场替换。
- 句子里夹带的产品名（"Fable 5.2 is here…" → "《Fable 5.2》……"）术语表管不到，后续可考虑"术语保护"：翻译前把专有名词换成占位符、翻译后还原。

## 翻译过滤（`filter.rs`，规划中，2026-11-18 定稿）

要解决的问题：一段文字该不该翻。现状是悬浮窗 `layout::needs_translation` 和沉浸模式 `inject.js` 的 `worth` 各有一套规则，已经不一致；只在目标为中文时才能识别"已是目标语言"（目标为日语时日文照样送翻，韩文谚文完全识别不了）；不带数字的品牌名（Claude、GitHub）没有保护；悬浮窗模式没有任何可配置项；被跳过的文字说不出原因。

**不接规则引擎，也不接外部决策模型。** 判断维度少（语言、字符类型、所在区域、专有名词），又要求微秒级、可解释、离线。规则引擎多一套 DSL 和依赖却管不了真正难的部分；外部决策模型（如 TypeSafe Jev，闭源云端 API，单次 70~500ms，厂商自报）每段调用一次比直接翻译还慢，也违背"默认离线、免 key"。

### 统一入口

两种模式都经过 `translate_batch_with_fallback`，在它最前面加一步：

```
filter::classify(文本, 上下文{目标语言, 应用, 模式}) → 翻译 | 保留原文(原因)
```

判为保留原文的直接原样返回，不查术语表、不查库、不请求引擎。规则只有 Rust 这一份：`layout::needs_translation` 改为调用它；`inject.js` 的 `worth` 只做廉价预过滤（少往主程序送字），以 Rust 的判断为准。

### 分层判断（越靠前优先级越高）

| 层 | 内容 | 举例 |
|---|---|---|
| 0. 结构区域 | 沉浸模式的 SKIP 选择器 + `skip_selectors`（在页面里判断，不进 `classify`）；悬浮窗没有结构信息 | 代码块、输入框、`.notranslate` |
| 1. 用户规则 | `keep_terms`（不翻译词表，整条匹配）、`keep_patterns`（正则）、`force_translate`（强制翻译，压过下面各层）；全局 + 按应用两级 | Claude、GitHub、`^v\d+` |
| 2. 内置规则 | 没有字母 / 字母少于 2 个、URL、邮箱、路径、文件名、版本号、变量名（驼峰、下划线）、带数字的 3 词以内短文本、超长文本 | `C:\foo`、`camelCase`、`Node 22` |
| 3. 语言识别 | `whatlang` 判断是否已是目标语言，任何目标语言通用（取代现在只认中日文的占比判断）；文本过短或置信度低时不下结论，交给下一层 | 目标日语时的日文 |
| 4. 交给引擎 | 前面都没定下来就翻译。**引擎译文与原文相同**（专有名词、已是目标语言）即记入译文库并标为"保留原文（引擎原样返回）"，下次直接命中；但原文含有与目标语言不同的文字系统时（目标英文、原文夹着中文）不算，先指定原文语言重试（见"沉浸模式"通道一的兼容性验证） | 品牌名、产品名 |

- **拿不准时默认翻译**：漏翻用户很难察觉，误翻一眼可见、一键可纠；第 4 层的自动学习会让误翻越来越少。
- **每个判断都带原因**（用户词表 / 用户正则 / 像路径 / 像版本号 / 已是目标语言 / 引擎原样返回 / 模型判断……），写日志，并供 M3 管理界面展示"为什么没翻"；界面提供"改为翻译 / 改为不翻"，写回第 1 层规则。
- 按应用：沉浸模式按 `immersive.targets[]`；悬浮窗按框下窗口所属进程名（`capture_under` 已能拿到窗口句柄）。
- 译文库 `translations` 表增加判定来源（引擎 / 大模型 / 手工 / 引擎原样返回），"保留原文"条目与普通译文同样参与命中。

### 句内专有名词（第二步）

整句要翻、其中的词要保留（"Open Claude Code settings"）：送引擎前把命中 `keep_terms` 的词替换为占位符，译后还原。各引擎对占位符的保留程度不同，需逐个实测后再启用；大模型引擎直接在提示词里给出不翻译词表，不用占位符。

## 沉浸模式（`immersive/`）

思路参考 Android 上的 LSPosed 文字替换模块：在目标应用**自己的进程里**拦截文字，替换成译文后再交给应用渲染，软件本体（exe、资源包）一个字节都不改。Windows 上界面框架很杂，按"通道"逐个接入，接管不了的回退悬浮窗模式。

### 通道一：Electron / Chromium 内核（已实现，首个适配 reclaude 客户端）

1. 目标应用带 `--remote-debugging-port=<端口>` 启动（只监听 127.0.0.1）。reclaude 启动客户端时会带自己的代理、用户数据目录等参数，没法直接追加，所以设置窗口的"以沉浸模式启动/重启"（`launch.rs`）会：读取正在运行的主进程（命令行不带 `--type=` 的那个）完整命令行，把参数记进配置的 `args`；替用户退出应用（Electron 单实例，不退出的话新进程会把参数转交旧实例后自行退出）：先向它的顶层窗口发 `WM_CLOSE`，4 秒内没退（带托盘的应用关窗口只是藏起来）就结束该程序的全部进程；再用同样的参数加上调试端口重新打开（2026-11-18 起不再要求用户手动退出）。`scripts/immersive-launch.ps1` 是同一流程的脚本版，保留备用。
2. 随译启动后为每个配置的目标开守护任务，每 2 秒轮询 `http://127.0.0.1:<端口>/json/list`（必须直连，环境变量里的代理会把本机请求也转走），对每个新出现的页面目标（page / iframe / webview）建一条 CDP 连接：
   - `Runtime.addBinding`（`executionContextName` = 隔离环境名）：页面脚本通过 `__tfSend()` 把原文发回主程序；
   - `Page.addScriptToEvaluateOnNewDocument`（`worldName` = 隔离环境名）：以后每次刷新/跳转自动注入；
   - 对已加载的文档，逐个框架 `Page.createIsolatedWorld` + `Runtime.evaluate` 注入一次。
3. `inject.js` 运行在**隔离环境**（isolated world）：与页面脚本互不可见、只共享 DOM，不污染页面全局变量，也不受页面 CSP 限制。它遍历文本节点和 `placeholder` / `title` 属性，`MutationObserver` 持续跟踪新增节点、文字和属性变化：
   - 先查页面内缓存（注入时预加载本地库最近常用的 5000 条），命中就在观察回调里当场替换，渲染前完成，不闪原文；
   - **分片处理，不卡页面**：脚本和页面共用主线程，切页时页面一次挂载成千上万个节点。观察回调只同步处理一片（约 8ms，按文档顺序，首屏优先），剩下的用 `MessageChannel` 排到后续任务里接着做，每片同样不超过 8ms；节点记录挂在节点自身（隔离环境里的属性，页面看不见），节点被页面丢弃后随之回收，来回切页不会越积越多；"是否值得翻译"的判断按原文记忆。实测（6000 个文字节点的模拟会话页）观察回调的同步开销从约 55ms 降到约 9ms，到下一帧的时间从约 227ms 降到约 189ms（不注入为约 149ms），且不再随切页次数增长。reclaude 自身切页就要 100–400ms（React 渲染、zod 校验等），这部分与翻译无关；
   - 未命中的攒 30ms 一批（每批最多 200 条）发给主程序，主程序查库/翻译后用 `__tf.receive()` 回填；失败时 `__tf.failed()`，10 秒后重试；
   - 记录每个节点的原文和"我们写进去的译文"：节点内容等于我们写入的值时忽略（避免自触发），被页面改成别的值就当新原文重翻；
   - 首尾空白原样保留，只翻中间部分；
   - 不碰的区域：`script/style/code/pre/kbd/samp/textarea/input/select/svg/canvas`、可编辑区（`contenteditable`，用户正在输入的内容绝不能改）、`translate="no"` / `.notranslate`（写在 `<html>` / `<body>` 上的不算，见下文兼容性验证），内置的代码编辑器与终端正文（Monaco、xterm、CodeMirror 5、Ace），以及配置里的 `skip_selectors`；`select` 整个跳过，因为没有 `value` 属性的 `option` 改文字会连带改掉提交值；
   - 过滤规则与悬浮窗一致（字母少于 2 个、目标为中文时本身以中日文为主的不翻），另外单个"词"像路径、文件名、版本号、变量名的不翻，带数字的 3 词以内短文本（"Opus 5.5"、"Node 22"，多为产品/型号名）也不翻（两边实际已不一致，将统一到 `filter.rs`，`inject.js` 只保留廉价预过滤，见"翻译过滤"一节）；
   - `__tf.setEnabled(false)` 把所有改过的文字恢复原文并停止监听，`true` 时重新全量扫描。
4. 已知限制与风险：
   - 改的是界面上的 DOM，复制界面文字会复制到译文；
   - 以文本节点为单位翻译，一句话被 `<b>` / `<a>` 拆成几段时译文会被切碎（界面按钮、菜单基本不受影响，长段正文可能受影响，必要时用 `skip_selectors` 排除）；
   - Canvas 渲染的内容（在线文档画布等）没有 DOM 文本，接管不了；
   - 调试端口开着时，本机任何程序都能通过它操控该应用（包括已登录的账号），用完建议照常重启应用关掉端口。
5. **兼容性验证（2026-11-18，本机 10 个 Electron 应用，目标语言设为英文以便验证中文界面）**：

   | 应用 | 调试端口 | 接管与翻译 | 备注 |
   |---|---|---|---|
   | VS Code | ✅ | ✅ 菜单、状态栏 | 编辑区正文、文件名不翻（符合预期） |
   | Trae（VS Code 衍生） | ✅ | ✅ | 首次启动的引导页 |
   | MarkText | ✅ | ✅ | 中英混排的条目被引擎原样返回，见下 |
   | MQTTX | ✅ | ✅ | 英文界面，无需翻译 |
   | Apifox | ✅ | ✅（修复后） | 根节点 `translate="no"`；验证中途界面自己变成日文并重启，原因未明 |
   | OpenCode | ✅ | ✅ | — |
   | Next AI Draw.io | ✅ | ✅ | 画布是 SVG，不翻（符合预期） |

   发现并已修复的问题（`inject.js`、`session.rs`）：
   - **根节点的 `translate="no"`**：不少应用在 `<html>` 上写它，只为不让浏览器弹自带翻译提示，照它跳过就整页不翻。改为只认 `<html>` / `<body>` 以下元素上的声明。
   - **中文整句被当成标识符**：中文不用空格分词，"您首先会创建什么..."、"搜索对话..."里的点号被"单个词像文件名"规则命中；"空格: 4"、"第 1 页"、"7月10日"被"带数字的 3 词以内短文本"规则命中；"VibCode分支原型：…"被驼峰规则命中。改为：含中日文的文本只按路径符号和文件扩展名（"海鸥3.0.md"）判断为标识符，不用数字和驼峰规则。

   - **地址为空的隐藏页面**（Apifox 有两个）：`Runtime.enable` 不响应、超时报错，改为不接管。

   未解决、留作后续：

### 管理（运行器、身份校验、状态、托盘与设置窗口）

- **运行器**：配置里每个应用对应一个运行器，各有开关（`enabled`）、原文/译文状态和运行状态。改配置后 `immersive::reload` 按"应用配置 + 目标语言 + 是否启用"的指纹比较，只重启有变化的应用；术语表的增删改算出差异后直接推送到已打开的页面（`__tf.patch`），不重启。
- **身份校验**：每 2 秒探测一次。用 `GetExtendedTcpTable` 查出调试端口的监听进程，再用 `QueryFullProcessImageNameW` 取它的程序路径，必须与配置的 `exe` 一致才接管，否则状态为"端口冲突"并拒绝接管（实测：Python 占用端口时被正确拦下）。没配 `exe` 时只能按端口接管。
- **状态**：总开关已关 / 已停用 / 未运行 / 未以沉浸模式启动（进程在但没开端口）/ 端口冲突 / 正在重启 / 已接管（附页面列表、本次回填条数、请求引擎次数）。状态变化通过 `immersive-status` 事件推给设置窗口，配置被托盘或启动流程改动时发 `config-changed` 让设置窗口重读。
- **停用与卸载**：停用、删除、改配置或退出时，会话对每个隔离环境执行 `__tf.dispose(true)` 恢复原文，然后断开连接。写端结束后必须主动发关闭帧，否则连接不断，CDP 登记的自动注入一直有效（实测踩过：停用后刷新页面又被翻译）。运行器被释放时"原文/译文"通道也会关闭，会话要把它同样当作停止信号处理，不能直接退出（实测踩过：停用时偶发不恢复原文）。
- **旧脚本让位**：重新接管时会在新的隔离环境里再注入一份脚本，隔离环境之间互相看不见，新脚本启动时通过共享 DOM 上的自定义事件通知旧脚本恢复原文并卸载，避免两份脚本同时改写页面。
- **托盘**：框选翻译、"沉浸模式：显示译文"（全局切换）、每个应用一个勾选项（单独开关，括号里显示状态）、设置、退出（先让所有页面恢复原文再退出）。左键单击托盘图标打开设置窗口。
- **设置窗口**（`settings.html` + `src/settings/`，带 `--settings` 参数启动时直接打开）。导航：概览 / 悬浮窗模式 / 沉浸模式 / 翻译引擎 / 译文库 / 术语表 / 常规；页面标题固定在顶部，滚动后右下角出现"回到顶部"。简单设置改完即保存，没有单独的保存按钮。`design/settings-preview/` 是模拟后端的预览页，可在普通浏览器里调界面（不参与打包）。
  - **用户不一定知道能填什么的参数，一律给出可选项，同时允许自己填写**（`ui.ts` 的 `combo`：可输入的下拉框，输入时筛选候选）：微软翻译的区域（Azure 区域列表）；接口地址（大模型列常见 OpenAI 兼容服务商，微软列全球 / 数据驻留 / Azure 中国端点，DeepL 列免费版 / 专业版，DeepLX 列本机默认端口）；大模型的模型（点按钮调 `llm_models` 命令，`GET {base_url}/models` 现取列表，按地址 + 密钥缓存）；代理（先选跟随全局 / 直连 / 系统代理 / 自定义，自定义再填地址并提示常见本机代理端口）。快捷键用录制框（点一下直接按组合键，`hotkeyInput`），沉浸模式的程序路径可点"浏览"用系统文件框选 .exe（`pick_exe`）。
  - 概览（仪表盘）：悬浮窗（打开中的翻译框数、开始框选、全部关闭）、沉浸模式（总开关、接管数、全部切换原文/译文）、翻译方式（翻译引擎 / 大模型切换、主用引擎、测速）、目标语言、大模型（模型、接口、密钥是否已填）、译文库与术语统计；
  - 悬浮窗模式提供开始框选（先最小化设置窗口）、关闭全部翻译框、框选快捷键、框内鼠标操作（新建框的默认值）、识别方式（视觉直译预留，暂不可选）和识别语言（列出系统已安装的 OCR 语言）。
  - 沉浸模式：总开关、全部显示原文/译文、切换快捷键、应用卡片（状态徽标、程序路径、端口、页面列表、回填计数、启用开关、以沉浸模式启动/重启、单独切换原文/译文、编辑、删除）；识别正在运行的应用、手动添加、编辑都在对话框里完成；
  - 翻译引擎：翻译方式（"翻译引擎"或"大模型"，由主用引擎类型推出：切到大模型时大模型做主用、原来的传统引擎顺序整体变成回退）、传统引擎为一张列表——左侧拖动手柄排序、右侧开关启用 / 停用，启用的引擎从上到下即调用顺序（首个即主用，其余依次回退；大模型方式下整条作为回退），启用前必须测试通过，至少保留一个启用，点开可编辑参数；大模型配置（接口地址、密钥、模型、代理），每个引擎可一键测试（固定英文句子试翻，显示耗时）；
  - 译文库：搜索原文或译文、只看手工译文、分页、直接改译（标记为手工译文并立即推送到页面）、删除单条（页面重新翻译）、清空（可保留手工译文）；
  - 术语表：自定义术语增删改、内置术语表开关与查看；
  - 常规：界面语言、目标语言、开机自启动、网络代理（全局：直连 / 系统代理 / 自定义地址）、译文库开关、文件位置（显示文件大小、在资源管理器中打开）。译文库可通过系统文件夹选择框换位置，连同文件一起搬过去（配置 `store_dir`，留空 = 数据目录）；配置文件位置固定。

### 随译开机自启动（Windows）

- 设置 → 常规的开关默认关闭。开启时为当前 Windows 用户登记随译的可执行文件，登录后启动到托盘。
- 设置页查询 Windows 启动项，识别系统中的停用状态；路径或参数发生变化后，可替换或移除旧启动项。设定不写入 `config.json`。
- 便携模式不修改启动项。卸载前可在常规页关闭自启动；安装包目前不会清除该项。

### 沉浸模式无感启动与后续方案

目标：用户在设置里添加一个应用后，以后照常打开它就自动处于沉浸模式，不用每次跑脚本；关掉后能干净还原。适用于需要带启动参数的通道（目前是 Electron / Chromium）。

**为什么不能"改一处就完事"**：一个应用的启动入口很多——开始菜单、桌面、任务栏固定的快捷方式，开机自启，链接协议（如 `claude://`），第三方启动器（如 `reclaude app`），以及自动更新后应用自己重启。只改某一处，从别的入口打开照样不带端口。另外调试端口一旦写进入口就**常开**，即使随译没运行、沉浸模式已关，本机程序也能通过它操控应用。所以采用"用户主动开启 + 改写入口参数 + 可还原 + 兜底重启"的组合，不做静默的永久修改。

1. **按应用开关"以后自动以沉浸模式启动"（默认关）**。开启时改写该应用的启动入口，追加 `--remote-debugging-port=<端口>`：
   - 开始菜单、桌面、任务栏固定（`%APPDATA%\Microsoft\Internet Explorer\Quick Launch\User Pinned\TaskBar`）里指向该程序的 `.lnk`：只改"参数"字段，目标、工作目录、图标不动；
   - Squirrel 安装的 Electron 应用（快捷方式指向 `Update.exe --processStart xxx.exe`）：改为追加 `--process-start-args "--remote-debugging-port=<端口>"`，直接追加参数传不到应用；
   - 开机自启项（`HKCU\...\Run`、启动文件夹）里指向该程序的条目一并处理。
2. **还原清单**：每改一处，先把原值记入 `~/.translate-anything/patched-entries.json`（位置：文件路径或注册表键、原参数、写入后的参数、所属应用、时间）。关闭开关、删除该应用、卸载随译时按清单逐项还原；还原前先比对当前值是否仍等于"我们写入的值"，已被用户或安装程序改过的不覆盖，跳过并在界面提示。
3. **自愈**：应用更新常会重建快捷方式、冲掉参数。随译每次启动时对开启了此项的应用重新检查入口，参数丢失就补回并更新清单。
4. **兜底：检测到没带端口就自动重启（已实现，2026-11-18）**。守护任务发现目标应用主进程在运行、调试端口却不通（从未改写或改不到的入口打开）时：
   - 主进程启动不到 30 秒且该应用开着 `auto_relaunch`（默认开）：先请求应用关闭，退出后带端口重开。未能正常退出时停止自动重启，用户可手动处理。两次自动尝试至少间隔 2 分钟，防止反复重启。
   - 更早就在运行的（如随译比应用晚启动）不自动动它，设置窗口显示"以沉浸模式重启"按钮，点一下即替用户退出并重开；弹通知未做。
   - 与入口改写相比，这种方式只在随译运行、该应用启用时才开端口，入口文件一个不改；代价是应用启动时多闪一次。入口改写（第 1–3 条）仍按规划保留，作为不想闪的用户的可选项。
5. **启动器优先**：目标应用由第三方启动器拉起、且该启动器支持配置额外参数时，在设置界面提示用户在启动器里加一次端口，比逐个改快捷方式更稳。是否支持取决于启动器本身。
6. **降低端口风险**：
   - 新添加的应用分配随机端口（避开常用端口，写入配置），不再统一用 39222；
   - 开启前在界面明确提示"开启后本机程序可通过调试端口操控该应用（含已登录账号）"；
   - 改写入口用的是普通参数：随译被删掉时应用仍能正常启动，只是多开一个端口，不会出现"快捷方式打不开"。因此**不采用**"快捷方式改指向随译自带启动器"的做法。
7. **不采用**：
   - IFEO（`Image File Execution Options` 的 `Debugger` 键）劫持启动：能覆盖所有入口，但需管理员权限，且是恶意软件常用手法，易被杀软报毒；
   - 向运行中的进程注入代码临时开启调试端口：依赖各 Electron 应用的内部实现和安全开关（fuses），不稳定，同样易被拦截。
8. **Chrome 浏览器本身作为目标时**：新版 Chrome 不允许在默认用户数据目录上开调试端口，必须另配 `--user-data-dir`（等于换一份浏览器资料），体验不是无感的；这类目标改走浏览器扩展通道（见"后续通道"的通道三），不走调试端口。

#### 通道二：WebView2 / CEF（复用 CDP，已实现，2026-11-18）

`cdp.rs`、`inject.js`、会话与管理逻辑全部复用，只改"怎么带上调试端口"和"怎么识别应用"（`procs.rs` / `launch.rs`）：

- **类型判断**（`procs::detect_kind`，按此顺序）：
  - Electron：程序目录（或其下一级，新版 VS Code 把资源放在以提交号命名的子目录里）有 `resources\app.asar` 或 `resources\app`，并有 Chromium 资源包；
  - CEF：程序目录有 `libcef.dll`；
  - WebView2：程序目录或其下一级有 `WebView2Loader.dll` / `Microsoft.Web.WebView2.Core.dll`（.NET 程序），或程序文件里有加载器要用的 `EmbeddedBrowserWebView` 字样（Tauri 这类静态链接加载器的）。
- **带端口**（`launch.rs`）：Electron / CEF 加命令行参数；WebView2 给启动的进程设环境变量 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=<端口>`（保留用户原有的附加参数）。只设在由随译拉起的进程上，**不写进用户级环境变量**，否则本机所有 WebView2 程序都会抢同一个端口。
- **识别运行中的应用**（`procs::running_apps`，设置窗口"识别正在运行的应用"）：WebView2 从 `msedgewebview2.exe` 浏览器主进程（命令行不带 `--type=`）的父进程找到宿主程序，排除系统目录下的程序（资源管理器、开始菜单、小组件也用 WebView2）；Electron / CEF 按目录特征，CEF 排除名字带 helper / subprocess / crashpad 等的辅助进程。列表上标出类型；"已开端口"只报确实在监听、且属于该程序的端口。
- **身份校验**（`procs::owned_by`）：监听端口的进程是配置的程序本身，或沿父进程链往上 4 层内能找到它。WebView2 应用监听端口的是 `msedgewebview2.exe`，Steam 这类把 CEF 放在辅助进程里的也一样。
- 不接管 `edge://` 内部页面。
- **实测（2026-11-18）**：

  | 应用 | 类型 | 结果 |
  |---|---|---|
  | CC Switch（Tauri） | WebView2 | ✅ 环境变量生效，监听进程 `msedgewebview2.exe` → 父进程 `cc-switch.exe`，校验通过，中文界面原地译成英文 |
  | Tiny RDM（Wails） | WebView2 | ❌ 端口没开：Wails 用自己的 Go 版加载器，不读这个环境变量 |
  | NVIDIA App | CEF | ❌ 主进程带上了参数，但程序不把命令行交给 CEF，端口没开 |
  | 识别 | — | Clash Verge、UU 加速器、Listary（.NET）、GameViewer 判为 WebView2；NVIDIA Overlay 判为 CEF |

- **遗留**：
  - Wails 这类自带加载器的应用：WebView2 运行时还会读注册表策略 `HKCU\Software\Policies\Microsoft\Edge\WebView2\AdditionalBrowserArguments`（值名为程序名），可在启动前临时写入、端口打开后删除，待验证；这是写策略键，要按"无感启动"的还原清单管理。
  - CEF 应用是否认命令行参数要逐个看；Steam 用自己的开关 `-cef-enable-remote-debugging`（固定端口 8080），可做成已知应用预设。
  - 一个程序建了多个 WebView2 环境（不同用户数据目录）时，只有第一个能拿到端口，待遇到实例再看。
  - 自动重启（`auto_relaunch`）对 WebView2 同样适用：结束的是宿主程序，WebView2 子进程随之退出；重开时走同一个 `launch`，自动带上环境变量。
- 无感启动同"无感启动"一节；WebView2 应用要改的是环境变量而不是参数，快捷方式改写不了，只能走"检测到没带端口就重启"。

#### 通道三：浏览器扩展

日常浏览器不走 CDP：新版 Chrome 不允许在默认用户数据目录上开调试端口；而且调试端口开着时，本机任何程序都能读到用户所有已登录网站的数据，风险远大于单个 Electron 应用。所以浏览器走扩展。

扩展既是沉浸模式的一个通道，也是一个能单独使用的产品，目标是全面超越"沉浸式翻译"，见独立的"浏览器扩展"一节。

#### 通道四：无障碍接口贴译文（UIA / AX / AT-SPI）

系统给读屏软件用的无障碍接口能读出大多数原生程序的文字和每段文字的屏幕坐标。**不注入、不改目标程序**，不会把它弄崩，也不会被杀软拦截；不需要 OCR，原文准确，位置精确到控件。普通文字控件只读，所以显示上是"在原位置贴一层译文"，不是程序里的文字真的变了。介于悬浮窗和原地改写之间，作为原生程序的通用兜底。

| 平台 | 接口 | 覆盖较好的 | 覆盖一般的 |
|---|---|---|---|
| Windows | UI Automation | Win32 标准控件、WinForms、WPF、UWP / WinUI、Office、资源管理器、系统设置 | Qt（需程序开启无障碍）、Java（走 Java Access Bridge） |
| macOS | 辅助功能接口（`AXUIElement`） | AppKit、SwiftUI、Catalyst、Office for Mac | Qt、Java |
| Linux | AT-SPI2（D-Bus） | GTK、Qt（需开启无障碍） | Wayland 下通常拿不到全局坐标，基本失效 |

- **流程**：取目标窗口 → 遍历文字元素，一次批量取文字和坐标（UIA 用 `CacheRequest`，跨进程逐个取属性很慢）→ 交给现有的过滤、术语表、译文库、引擎链 → 用翻译框的渲染方式在原位置贴译文（复用 `live.rs` / 前端的版面渲染，只是文字来源从 OCR 换成接口）。
- **跟随变化**：订阅结构变化、文字变化、位置变化事件（UIA 事件 / `AXObserver` / AT-SPI 信号），只处理变动的元素；事件太密时合并成一轮。不轮询整棵树，空闲时不空转。
- **管理**：和其他通道一样按应用开关，出现在沉浸模式的应用卡片里；体验标为"贴译文"，与"原地改写"区分。
- **限制**：
  - 自绘界面、游戏不暴露文字，自动退回悬浮窗；
  - Chromium / Electron 只在开启无障碍时才暴露文字，这类程序走 CDP，不走这条；
  - Windows 上以管理员身份运行的程序，普通权限的随译读不到；
  - macOS 要用户授予"辅助功能"权限。

#### 通道五、六：进程内注入（Windows 专属）

| 通道 | 做法 | 覆盖 |
|---|---|---|
| XAML | 官方 XAML 诊断接口（`InitializeXamlDiagnosticsEx`）遍历可视树，改 `TextBlock.Text` 等 | WPF、UWP、WinUI 3 |
| Win32 原生 | 注入 DLL，hook `SetWindowTextW` / 菜单 API / `MessageBoxW` / `DrawTextW` / `ExtTextOutW` | 传统 Win32、MFC、WinForms 底层控件 |
| DirectWrite | hook `IDWriteFactory::CreateTextLayout` 等 | 用 DirectWrite 排版的现代程序 |
| Qt | hook `QLabel::setText` / `QAbstractButton::setText` 等导出函数 | Qt 程序 |

XAML 用的是官方诊断接口，相对稳，优先做。其余三种是 hook，**只在用户对某个应用主动开启时使用**，并提示风险。这类程序在通道四下已经能贴译文，hook 只是把体验从"贴译文"提到"原地改写"，所以等有具体想接的软件再做。

进程内 hook 的共同难点：hook 函数里不能同步等网络，只能"缓存命中当场替换，未命中先显示原文、异步翻译后触发重绘"；代码跑在别人进程里，出错会连累目标程序崩溃；注入易被杀软拦截，带反作弊的游戏必须排除；32 位程序要单独一套 DLL。macOS（系统完整性保护、签名校验）基本做不到这类注入；Linux 技术上可行（`LD_PRELOAD`、GTK 模块、Qt 插件），但发行版和沙盒格式太零散，不规划。

## 浏览器扩展（`extension/`，规划中，2026-11-18）

### 对方结构上的短板，也是随译的突破口

1. **只在浏览器和自家 App 里**：桌面软件、游戏、任意画面它都翻不了。随译用同一套术语表、译文库、快捷键覆盖浏览器内外，在桌面软件里改过的译法到网页上照样生效。
2. **依赖云端和额度**：免费版每日有上限，好引擎靠会员。随译有本地译文库，看过的文字再看不请求、渲染前就替换好，不闪原文；还有离线翻译；免 key 引擎和用户自己的 key 直连，没有账号、没有额度。
3. **隐私**：随译没有自己的服务器，内容只在本机和用户选的引擎之间往来；可以按网站设成只用离线翻译。
4. **会议和音视频**：浏览器只能处理网页里的会议和视频。随译能采集系统音频，桌面版 Zoom、Teams、微信通话和本地播放器也能翻（依赖后续的音频同传规划）。
5. **文档在桌面端处理**：把文件拖进随译即可，不受浏览器内存限制，可以批量处理，本机 OCR 不上传。
6. **可解释、可纠正**：每段文字为什么没翻都能查到原因，可以一键改为翻译或不翻；改一处译文，所有地方都生效。

### 架构

- **两种运行方式**：
  - **单独使用**：没装随译也能用，面向商店用户和还没有桌面版的平台（ChromeOS、Linux 上的 Wayland 等）。扩展自带引擎调用、译文库（存 IndexedDB，有上限）和设置页。
  - **连接随译**：通过 native messaging 连接（浏览器按注册的清单拉起随译自带的中转小程序，不开端口，只有本扩展能连）。连上后自动改用随译的引擎链、译文库、术语表、过滤规则和离线翻译，设置统一在随译里管。
- **共用核心，不写两套**：把 Rust 里与平台无关的部分（过滤规则、术语表匹配、引擎请求的构造与解析、分段）拆成独立的 crate，桌面端原生编译，扩展编译成 WASM；网络请求由宿主提供（桌面用 reqwest，扩展用 fetch）。WASM 的体积是否可接受，先做原型确认。
- 页面脚本由 `inject.js` 演进而来；段落级翻译做好后，桌面端的 CDP 通道一起受益。
- 界面文案共用 `src/i18n/*.json`。
- **体积与占用**：功能按模块按需加载，字幕、图片、划词等用到时才注入，不在每个页面常驻大脚本；本地译文库设上限，按最近使用清理。
- 免 key 接口在扩展里直接请求，需要在清单里声明对应域名的权限；不使用网上流传的 key（沿用已定决策第 3 条）。不参考对方的闭源代码；如使用开源组件，先核实许可证（AGPL 之类会传染）。
- **共存**：检测到页面已被其他翻译扩展处理过，就跳过该页面，不重复翻译。

### 需要用户拍板

1. ~~要不要做自己的服务~~ **已定（2026-11-18）：要做，但暂不考虑**。等功能完善、或出现需要账号的功能（内置 AI 额度、多设备同步译文库和术语表等）时再做。在那之前靠免 key 引擎和用户自己的 key；架构上给"随译官方服务"留一个引擎类型和一处登录入口即可，不提前建账号体系。

## 语言包模式（`langpack/`，规划中，2026-11-18 定稿）

即"汉化"：直接翻译目标软件自带的语言文件，软件按自己的语言机制加载译文。与沉浸模式相比：没有运行时开销、不开调试端口、不注入；按"键 + 整句"翻译，带占位符和复数结构，不会被拆碎；还没显示过的文字也一并译好。代价是**要改软件的资源文件**，与沉浸模式"本体一个字节都不改"的原则相反，所以定为**第三种模式**：按应用由用户主动开启，随时一键还原，与悬浮窗、沉浸模式并存，不取代它们。

### 三种操作

| 操作 | 做法 | 可靠程度 |
|---|---|---|
| 替换 | 选一种已有语言（如 en），保留键，内容换成目标语言译文 | 最可靠：程序本来就会加载这份文件 |
| 补全 | 目标语言文件已存在但条目不全，只翻译缺的条目，已有的人工译文不动 | 可靠 |
| 新增 | 以条目最全的已有语言为源，新写一份目标语言文件 | 看程序：语言列表写死在代码里时多放一个文件不会被读到 |

- 扫描程序目录，列出读到的已有语言及各自条目数，供用户选源语言（默认条目最全的那份，通常是 en）和操作。
- "新增"之前先判断该格式 / 程序是否按文件是否存在来发现语言（Qt、gettext、.NET 附属程序集一般是；Electron 应用多半不是），判断不了时提示改用"替换"。

### 格式适配器

按格式逐个接入，与沉浸模式的"通道"思路一致。每个适配器负责：在程序目录里发现语言文件 → 读出（键、原文、可选的上下文）→ 按原格式写回，未翻译的条目、注释、顺序尽量保持原样。

| 格式 | 位置 | 备注 |
|---|---|---|
| JSON / YAML（平铺或嵌套，含 ICU MessageFormat） | 各类 Electron 应用、游戏 | 首批 |
| gettext `.po` / `.mo` | `locale/<语言>/LC_MESSAGES/` | 首批 |
| Qt `.qm` | `<程序>_<语言>.qm` | 二进制格式，自行读写，不依赖 Qt 工具链 |
| Java `.properties` | 散放或在 jar 内 | 改 jar 需重新打包 |
| .NET 附属程序集 | `<语言>/<程序>.resources.dll` | 需生成程序集，强名称签名有限制，后做 |
| PE 内的字符串表 / MUI | exe / dll 资源 | **不做**：改了破坏数字签名 |

### 翻译

- 复用 `translate_batch_with_fallback`、译文库、术语表、`filter.rs`。键名有语义（`menu.file.new`）时作为上下文；大模型引擎可整批翻译，并把同一文件里相邻条目当上下文。
- **占位符保护是硬性要求**：`{host}`、`%s`、`%1`、`{{name}}`、ICU 的 `plural` / `select` 结构、HTML 标签都先换成占位符，ICU 结构只翻译分支里的文字。译后校验占位符集合与原文一致，不一致的条目保留原文并记录原因。这套机制与"句内专有名词"共用。
- 翻译量大（一份常有上千条），后台执行，显示进度，可中断后续翻；已在译文库里的直接命中。

### 安全拦截与还原

- **改之前先检查，查到就拒绝并说明原因**：
  - Electron 开启了 `EnableEmbeddedAsarIntegrityValidation` / `OnlyLoadAppFromAsar`（读 exe 里的 fuse 标记）时，app.asar 一改程序就拒绝启动，不能改；
  - 语言文件本身带数字签名的；
  - 带反作弊的游戏。
- 软件装在 Program Files 等需要管理员权限的位置时，单独提示并按需申请提升，不静默提权。
- **备份与还原**沿用"无感启动"的还原清单（`patched-entries.json`）：写入前备份原文件并记下原哈希、写入后的哈希、程序版本。还原、关闭该应用的语言包、删除该应用、卸载随译时按清单还原；还原前比对当前文件是否仍是我们写入的版本，已被更新或用户改过的不覆盖，并在界面提示。
- **自愈**：软件更新会覆盖语言文件。随译启动时对开启了语言包的应用比对版本 / 哈希，被覆盖了就按新文件重新生成（只翻新增和变更的条目）。
- 生成的语言包只在本机使用，不提供分享或导出给他人，避免涉及软件厂商文案的版权问题。

### 实例：reclaude 客户端（Electron 45）

- 语言文件在 `resources/app.asar` 内的 `resources/i18n/*.json`（react-intl / ICU，键是哈希 ID，没有语义）；自带 `zh-Hans`，893 条，`en-US` 有 1310 条，中文缺约 32%。
- `claude.exe` 的 fuse 开着 asar 完整性校验和"只从 asar 加载"，**改不了文件**；这些文件也只管客户端外壳，对话主界面的文字来自 claude.ai 网页，不在本地。
- 结论：这个应用继续走沉浸模式。

### 运行时语言包（Electron / Chromium，设想，未验证）

文件改不了的 Electron 应用，可借沉浸模式已有的 CDP 连接，在程序加载语言资源时把内容换成译文（如用 `Fetch` 拦截网页请求的语言 JSON 并改写响应），不改磁盘上的文件，又能按整句和键翻译。但语言资源怎么加载（主进程读文件经 IPC 传入、打包进 JS、网络请求）各应用不同，需逐个实测后再定。

## 翻译 Provider 抽象

> OpenAI 兼容（大模型）引擎的批量翻译（2026-11-19）：把多条原文作为 JSON 字符串数组一次发出、要求返回等长数组（每组最多 40 条 / 6000 字，多组并发），
> 实时翻译框一屏几十段只需一两个请求；模型没按格式返回时该组改为逐条翻译（并发 4）。回复里的 `<think>…</think>` 会去掉；
> 鉴权失败（401/403）时提示核对密钥与接口地址是否同一家，接口为 `api.deepseek.com` 而密钥不是 `sk-` 开头时提示多半填了其他平台的密钥。

```rust
#[async_trait]
pub trait Translator: Send + Sync {
    async fn translate(&self, text: &str, target_lang: &str) -> Result<String, TranslateError>;
}
```

**默认不走大模型。** 引擎清单在 `translate::CATALOG`（id、中文名、是否需要 key、是否官方、需要的字段），前端可通过 `engine_catalog` 命令读取，供 M3 设置界面渲染。

| 引擎 id | 实现 | key | 国内直连 | 参考 |
|---|---|---|---|---|
| `edge`（默认） | `POST edge.microsoft.com/translate/translatetext?from=&to=..`，体 `["原文"]`，无鉴权；失败自动回退 `bing` | 免 | 能 | kiss-translator |
| `bing` | `GET cn.bing.com/translator` 抓 `IG`、`data-iid`、`params_AbusePreventionHelper=[key,token,ttl]` → `POST /ttranslatev3?isVertical=1&IG=&IID=` 表单；token 过半有效期刷新，响应 `statusCode==205` 重取 | 免 | 能 | Easydict、translate-shell |
| `google_free` | `GET translate.googleapis.com/translate_a/single?client=gtx&dt=t&dj=1&sl=auto&tl=..&q=..`，拼接 `sentences[].trans`；429/验证页给出提示；`base_url` 可换镜像 | 免 | 需代理 | pot-desktop、STranslate |
| `microsoft` | Azure Translator v3 官方 API，需 `api_key`、`region` | 需 | 能 | — |
| `deepl` | DeepL API v2，`:fx` 结尾 key 走免费端点 | 需 | 能 | pot-desktop |
| `deeplx` | 用户自建 DeepLX，`POST base_url {text,source_lang,target_lang}`，译文在 `data` | 可选令牌 | 视部署 | pot-desktop |
| `google` | Cloud Translation Basic v2 官方 API | 需 | 需代理 | — |
| `openai` | OpenAI 兼容 `/chat/completions`，需 `base_url`、`model` | 需 | 视服务商 | — |

- 2026-11-16 实测：`edge`、`bing` 直连可用，`google_free` 经 Clash 可用；Edge 的 `translate/auth` 已 404（pot-desktop 仍在用，已失效）。
- 免 key 接口都是非官方用法，近一年各开源项目均遇到过失效（Edge auth 404、DeepL jsonrpc 503、Google gtx 429），所以设计为**主引擎 + 回退链**，并保留官方 API。
- **不采用**：网上流传的 Google API key、逆向得到的微软签名私钥、伪装 DeepL iOS 客户端的接口。
- 传统引擎会逐行翻译，发送前用 `merge_lines` 把 OCR 硬换行合并成自然段；大模型直接收原文，由提示词处理。
- 代理分两层（2026-11-18 用户确认）：顶层 `proxy` 是全局代理，所有引擎默认走它（留空 = 直连；`system` = 跟随系统环境变量；其他 = 代理地址，如 Clash `http://127.0.0.1:7897`）。单个引擎的 `proxy` 留空 = 跟随全局；`direct` = 直连（如国内可直连的 `edge`、`bing`）；也可填 `system` 或自己的代理地址。由 `Config::provider` 统一解析。旧配置里引擎留空本来就是直连，而全局默认也是直连，所以无需迁移。
- 浮窗报错时逐个列出各引擎的失败原因，并附上识别出的原文。
- 配置决定一切，不在代码里写死任何服务商的 key。

### 引擎列表：普通引擎、AI 翻译、离线翻译混排（规划中，2026-11-18 定稿）

底层本来就是同一个 `Translator` 接口、同一条回退链，所以界面上也合成**一个列表**，不再分"翻译方式"二选一和两个列表：

- **一个列表，从上往下调用**：普通引擎、AI 翻译、离线翻译混排，拖动排序，出错换下一个，如"Bing 失败 → DeepSeek → 本地 Ollama → Edge"。
  第一项就是主用引擎，概览页的"翻译方式"改为显示"主用：xxx"。每项带类型标签（免费 / 官方 API / AI / 离线 / 视觉）。
- **可增删**：内置的 Edge、Bing 也能删，删了可再添加；至少保留一个已启用的项。每项可编辑、测试、开关、删除；启用前须测试通过（沿用现有规则）。
- **添加用弹窗**：先选类别（翻译引擎 / AI 翻译 / 离线翻译）→ 选具体服务（AI 翻译列出 DeepSeek、智谱、OpenAI、Ollama 等预设，带出接口地址和模型列表）→ 填参数 → 测试通过后加入列表。
  同一种服务可添加多份（如两个 DeepLX、两个大模型），配置里用 `"type"` 区分，键名随意（已支持）。
- **按单项冷却**：某项失败后几分钟内（暂定 3 分钟）直接跳过它；全部都在冷却中时仍按顺序尝试。
  AI 翻译混排在中间时，一次超时就要好几秒，没有这一条会拖慢整条链。普通引擎同样受益。
- **离线草稿开关**：列表里有离线项时才出现"先显示离线译文"开关（见"离线翻译"一节）。
- 混排后同一屏可能出现两种风格的译文（AI 失败回退到普通引擎），可以接受；界面已显示每次实际用的引擎。
- 配置结构不变：列表顺序 = `engine` + `fallback`，`engines` 存各项参数（停用的项参数保留，删除才移除）。

## AI 翻译（大模型引擎，可选，规划中，2026-11-18 定稿）

**界面上统称"AI 翻译"**（英文 AI translation），首次出现处说明是"用 ChatGPT、DeepSeek、Ollama 等大模型翻译，更通顺但较慢"——Edge、DeepL 和离线模型其实也是神经网络翻译，不能只靠名字区分。代码里的 `llm`、`openai` 等标识不改。

**AI 翻译只是可选引擎，默认链路仍是传统翻译引擎（`edge` → `bing` …），不改变已定决策。** 用户在引擎列表里添加 OpenAI 兼容服务（可添加多个），按自己想要的位置排进回退链；也可接本地模型（同样走 OpenAI 兼容接口）。

### "是否翻译"在本地与提示词之间的分工

- **确定的留在本地**：`filter.rs` 第 0~3 层、术语表、译文库照常先走一遍，只把剩下的送给模型——省 token、省延迟，用户规则百分之百生效，原因可解释。
- **语义判断交给提示词**：句内专有名词、混合语言、界面术语的译法、该不该保留原文。
- **结果回写本地**：模型判为保留原文的，记入译文库并标为"保留原文（模型判断）"，下次本地直接命中，不再问模型。

### 提示词与结构化输出

- 输入：编号列表 `[{id, text}]` + 不翻译词表（`keep_terms`）+ 术语表 + 少量上下文（应用名、页面标题、相邻文字）。
- 输出：JSON `[{id, keep, text}]`，`keep=true` 表示保留原文。
- Provider 接口新增批量结构化方法（如 `translate_items(items, ctx) -> [{keep, text}]`）；传统引擎用默认实现：调用 `translate_batch`，`keep = 译文 == 原文`。两类引擎对上层是同一个接口。
- **防注入**：页面文字和截图都可能夹带"忽略以上指令"之类的内容。提示词声明列表内容只是待翻译的数据；返回后校验 id 一一对应、条数一致、长度不离谱，不通过即视为该引擎失败，按回退链换下一个引擎。

### 悬浮窗：OCR 定位 + VLM 理解

**本机 OCR 始终保留，视觉模型不替代它**：
1. 原位覆盖需要每块的准确坐标、颜色和字号，VLM 给的坐标不可靠；
2. OCR 15~50ms，VLM 一次 1~5s，画面每变一次就要重新识别，逐帧调 VLM 做不到实时；
3. 先有本地 OCR 文字才能查译文库、术语表、跑过滤，命中的不必请求模型；没有它每次画面变化都得整图发给模型；
4. 滚动跟随、位移靠的是 OCR 出的文字块。

所以视觉能力加在"送翻译"这一步：**是引擎列表里单项的属性**（`vision: true`），不是顶层替代 OCR 的开关。

1. OCR 照常出块（文字、坐标、颜色、字号仍由 `layout.rs` 负责）；
2. 本地过滤 + 术语表 + 缓存先处理，**只把未命中的块**连同截图（可裁到这些块的外接区域）送给 VLM；
3. VLM **一次完成纠错 + 翻译**，按块 id 返回 `{id, keep, text, source?}`：借助图像纠正 OCR 错字、区分按钮/标题/正文、识别图标旁的产品名；`source` 是纠正后的原文（可选，只用于显示）。
   不拆成"VLM 只做 OCR、再交给别的引擎翻译"：那样调用两次、延迟翻倍，也浪费了"看着画面翻译"这个最大的价值。
   译文库的键仍是本机 OCR 原文，下次同一画面在本地直接命中。

- 链上走到开了视觉的项才附带截图，没开的项只发文字；视觉项失败照常换下一项，用的是同一批 OCR 结果。
- 开启视觉也须测试通过：测试时发一张小图，确认模型真能看图，避免给纯文本模型误开。
- 画面不变的块走缓存，实时刷新时只有新进入框内的文字才触发请求。

**视觉直译（F9）是悬浮窗的一种模式，不在引擎列表里**：专门对付本机 OCR 读不出来的画面（艺术字、游戏贴图文字、竖排日文、没装 OCR 语言包的语言）——不经 OCR、整图交给 VLM 翻译，译文在浮窗内集中显示，不原位覆盖。
它改变的是显示方式，所以放在「悬浮窗」设置页顶部："识别方式：本机 OCR（默认）/ 视觉直译"，配置 `mode: "ocr" | "vision"`。
选视觉直译时按列表顺序只用开了视觉的项，一个都没有就提示去添加。trait 增加 `translate_image(&self, png: &[u8], target_lang)`，默认返回"不支持"。

### 沉浸模式：LLM 批量 + 上下文

- 沿用现有批次（30ms 攒一批、每批最多 200 条），每条附相邻节点作上下文；同一句被 `<b>` / `<a>` 拆开的几个文本节点标为同组，让模型分别给出各段对应的译文，缓解"译文被切碎"。
- 仍然"先显示原文、异步回填"，大模型延迟高也不卡界面；译文库命中率高，稳定使用后大部分文字不再请求模型。

### 隐私

截图和界面文字会发给模型服务商，敏感程度高于传统翻译接口：AI 翻译与 VLM 可按应用开关；推荐对敏感应用使用本地模型、离线翻译或只用传统引擎。

## 离线翻译（规划中，2026-11-18 定稿）

动机：实测一轮悬浮窗翻译 1.1~1.2s，其中 Edge 请求占 0.87~0.93s（见"数据流"一节的耗时日志）；离线小模型一批几段短文本估计几十到 100 多 ms（待原型实测）。代价是质量低一档（英→中尤其明显）、要下载模型、加载后常驻内存。

**选型**：各家软件的离线翻译本质都是下载到本机的小型翻译模型，但大多不开放给其他程序：

| 方案 | 能否用 | 原因 |
|---|---|---|
| Google 翻译离线包 / ML Kit | 否 | 只有 Android / iOS |
| 微软翻译离线包 | 否 | 无对外接口；企业离线容器需申请、商用授权 |
| Chrome 端侧 Translator API | 否 | 只在 Chrome 网页里可用，要驱动用户的 Chrome，重且不稳 |
| **Firefox 本地翻译（Bergamot）** | **Windows 采用** | 引擎开源、模型由 Mozilla 公开发布，可直接集成，不需要用户装 Firefox；大量 Firefox 用户在用 |
| **Apple Translation 框架** | **macOS 移植时采用** | 系统自带、离线，与 Windows 用系统 OCR 同一思路 |
| Windows 系统接口 | — | 目前没有类似 `Windows.Media.Ocr` 的系统翻译接口 |

**界面**：
- 「离线翻译（本机）」是引擎列表中的一项，默认建议放在最后作断网兜底；至少下载一个语言包才能通过测试、启用。
- 展开后是语言包管理：按目标语言推荐常用方向（如 英→中、日→中），每个显示大小和状态（未下载 / 下载中 xx% / 已就绪），可下载、删除，并显示总占用；下载走全局代理。macOS 上是系统语言包，引导去系统里下载。
- 列表里有离线项时出现开关「先显示离线译文，联网结果回来后替换」，默认关。打开后体感速度由离线决定，最终质量由在线引擎或 AI 翻译决定；悬浮窗里草稿译文略淡，替换后恢复。
- 沉浸模式按应用可设「只用离线翻译」，敏感软件里的文字不离开本机。
- 概览页统计离线翻译的条数。

**架构**：
- `translate/offline.rs` 实现 `Translator`，内部按平台分 Windows（Bergamot）/ macOS（系统框架）；术语表、译文库、过滤等上游不变。
- 先用 `whatlang` 判断原文语言，没有对应语言包就交给链上下一项。
- 模型首次用到才加载，空闲几分钟后释放内存；模型放数据目录 `models/`（便携版在 `<程序目录>\data\models`），下载后校验。
- 译文库里离线译文标为**草稿**，之后在线引擎或 AI 翻译的结果可以覆盖，避免一次离线结果一直挡住更好的译文。
- "先离线、后替换"需要分两段返回的翻译接口（先草稿、再正式结果）：悬浮窗推送两次版面，沉浸模式回填两次。这是改动最大的一块。
- 限制：句内术语无法强制套用术语表，只有整句命中术语表才生效。

**先验证的风险**（先做原型实测速度、质量、体积，再正式接入）：
- Bergamot 是 C++ 项目，要在 Rust 里编译集成，并同时支持 x64 / ARM64 的发布流程；安装包增加量待原型确认。
- 核实 Mozilla 模型的使用许可。
- macOS 系统翻译框架能否在非 SwiftUI 程序里直接调用，移植时确认。

    },

- `engine`：主用引擎 id；`fallback`：失败后依次尝试的引擎；`engines`：各引擎参数，键为引擎 id。界面上三者合成一个可排序的引擎列表（见"引擎列表"一节）。
- 同一类型要配多份时（例如两个大模型服务），在条目里写 `"type": "openai"`，键名随意。
- 配置文件不存在时使用默认值（`edge`，免 key 开箱即用）；旧版 `provider` 单引擎写法仍兼容。
- `persist_cache`：是否使用译文本地库（默认开）。
- `builtin_glossary` / `glossary`：内置术语表开关、自定义术语表（见"术语表"一节）。
- `filter`（规划中）：翻译过滤用户规则（见"翻译过滤"一节）。`keep_terms` 不翻译词表、`keep_patterns` 正则、`force_translate` 强制翻译；`apps` 按悬浮窗框下窗口的进程名单独设置，与全局规则合并。
- `immersive`：沉浸模式。`enabled` 总开关；`hotkey` 译文/原文切换快捷键（默认 `Alt+Shift+T`）；`targets` 要接管的应用，每项 `name`、`enabled`（单独开关）、`exe`（程序路径，用于身份校验和启动）、`args`（启动参数，不含调试端口，运行时自动读取）、`port`（调试端口，不能重复）、`url_prefixes`（只处理这些地址开头的页面，留空 = 全部）、`skip_selectors`（额外不翻译的元素）、`filter`（该应用的过滤规则，规划中）、`auto_relaunch`（用户直接打开、没带端口时自动重启为沉浸模式，默认 `true`）、`auto_launch`（以后自动以沉浸模式启动，默认 `false`，规划中，见"无感启动"一节）。默认为空列表，不预置任何应用，由用户在设置窗口里检测或手动添加（2026-11-18 改定，此前默认带一项 reclaude 客户端）。已实现的字段都可以在设置窗口里改，保存后立即生效（快捷键除外）。
- `engines.<id>.vision`（规划中）：该 AI 翻译项是否支持图像输入，为真时悬浮窗模式附带截图；开启须测试通过（见"AI 翻译"一节）。
- `engines.<id>` 的 `"type": "offline"`（规划中）：离线翻译项；语言包放数据目录 `models/`，不写进配置。`offline_draft`（规划中，默认 `false`）：先显示离线译文、联网结果回来后替换。`immersive.targets[].offline_only`（规划中）：该应用只用离线翻译（见"离线翻译"一节）。
- `frame_click_through` 只设置新建翻译框的默认鼠标操作。`true`（默认）为鼠标穿透，`false` 为框内拖动。工具条的单框切换只修改当前窗口的状态。
- `mode`：悬浮窗识别方式，`ocr`（默认，本机 OCR）或 `vision`（视觉直译，规划中）。
- `ui_lang`：界面语言，如 `zh-CN`、`en`；留空 = 跟随系统（见"界面多语言"一节）。`target_lang` 在配置文件不存在时取系统语言（`zh-TW`/`zh-HK` 系统为 `zh-TW`，其他取语种，如 `ja`）。

## 界面多语言（`i18n.rs` + `src/i18n/`，2026-11-18）

- 文案：`src/i18n/<语言>.json`，扁平键值（如 `"tray.quit": "退出"`），占位符写 `{name}`。前端与 Rust 共用同一份：Rust 用 `include_str!` 编译进程序，前端不重复打包，启动时调 `ui_i18n` 命令一次拿到合并好回退的整份文案。
- 语言确定：设置（`ui_lang`）→ 系统界面语言（`GetUserDefaultUILanguage`）→ 同语种（`zh-TW` → `zh-CN`）→ `en`。缺键时回退到 `en` 的文案。自测可用环境变量 `TA_LOCALE=en-US` 覆盖系统语言。
- 用法：Rust `t!("key")`、`t!("key", name = x)`；前端 `t("key", { name })`，静态 HTML 用 `data-i18n` / `data-i18n-title` / `data-i18n-aria` / `data-i18n-placeholder`。
- 切换界面语言：保存后后端重建托盘菜单并发 `locale-changed` 事件，各窗口重新载入。
- 软件名用 `app.name`：中文为「随译」，其他为「Translate Anything」。语言名（目标语言下拉框等）用浏览器的 `Intl.DisplayNames` 按界面语言显示，不进语言文件。
- 不进语言文件的：控制台日志、注释、发给大模型的提示词。译文库的"来源"列存引擎 id，显示时再换成当前语言的名称（早期数据存的是中文名，原样显示）。
- 新增语言：在 `i18n.rs` 的 `LOCALES` 加一行并放同名 JSON；缺的键自动用英文。单元测试 `语言文件键一致` 保证 `en` 与 `zh-CN` 键完全一致、其他语言不多出键。

## 各平台覆盖范围（规划，2026-11-18）

各平台能做到什么程度。具体到每个模块怎么移植，见下一节"多平台打包与发布"。

### 体验等级

| 等级 | 含义 |
|---|---|
| **A 原地改写** | 译文直接出现在软件自己的界面里，排版、滚动、交互都和原文一样，几乎感觉不到翻译这一层 |
| **B 精准贴译文** | 读出软件里的真实文字和坐标，在原位置贴一层译文：原文准确、位置精确、自动跟随，不用框选，但译文只是贴在上面的一层 |
| **C 悬浮窗 OCR** | 任何画面都能翻，需要手动框选，会有识别误差 |
| **D 做不到** | — |

各平台都复用：翻译引擎、译文库、术语表、过滤规则、页面脚本（CDP 和浏览器扩展共用）。要分平台做的只有"拿到文字"和"显示译文"两层。

### Windows：上限最高，几乎全覆盖

| 等级 | 覆盖 | 做法 |
|---|---|---|
| A | Electron、WebView2、CEF 应用 | CDP（通道一、二） |
| A | 浏览器网页 | 浏览器扩展（通道三） |
| A | WPF、UWP、WinUI 3 | XAML 诊断接口 |
| A（用户按应用主动开启） | Win32、MFC、Qt | 进程内 hook |
| B | 其余大部分原生程序：Office、资源管理器、系统设置、WinForms、开了无障碍的 Qt、Java | UI Automation（Java 走 Java Access Bridge） |
| C | 游戏、视频、图片、远程桌面、扫描件 | 悬浮窗 |
| D | 带版权保护的视频（截屏为黑）、部分独占全屏游戏（悬浮窗盖不上去） | — |

典型的办公或开发用户，大部分使用时间在浏览器和 Chromium 系软件里，能做到 A；其余原生程序基本能做到 B，日常很少需要手动框选。限制：以管理员身份运行的程序，普通权限的随译读不到也注入不了。

### macOS：A、B 稳定，原生程序到 B 为止

| 等级 | 覆盖 | 做法 |
|---|---|---|
| A | Electron | CDP，按代码签名校验身份 |
| A | Chrome、Edge、Firefox、Safari 网页 | 浏览器扩展（Safari 用 Xcode 打包） |
| B | AppKit、SwiftUI、Catalyst 程序，Office for Mac；Qt、Java 效果一般 | 辅助功能接口（`AXUIElement` + `AXObserver`） |
| C | 其余所有画面 | ScreenCaptureKit + Vision OCR |
| D | 原生程序原地改写（系统完整性保护、签名校验拦注入）、带版权保护的视频、密码输入框 | — |

需要用户授予"屏幕录制"和"辅助功能"权限；发布需要签名和公证；不上 Mac App Store。

### Linux：取决于显示协议

| 等级 | 覆盖 | 做法 |
|---|---|---|
| A | Electron、浏览器网页 | CDP、浏览器扩展 |
| B | GTK、Qt（需开启无障碍） | AT-SPI2；Wayland 下通常拿不到全局坐标，基本失效 |
| C · X11 | 所有画面 | 截屏、置顶、鼠标穿透都没有障碍 |
| C · Wayland | 所有画面，体验降级 | 截屏走系统门户（要授权）；悬浮窗定位要靠 layer-shell（KDE 等支持，GNOME 不支持）；全局快捷键走门户接口 |

OCR 没有系统自带的，方案见"多平台打包与发布"的"需要用户拍板"第 2 条。体验分三档：X11 接近 Windows（少了 XAML 这类官方改写通道）；KDE Wayland 可用；GNOME Wayland 最弱，主要靠 Electron 和浏览器的 A 等级。

### Android（远期）：B 等级覆盖最广

| 等级 | 覆盖 | 做法 |
|---|---|---|
| A（需 root） | 几乎所有应用 | LSPosed hook `TextView.setText` 等（本项目最初参考的思路），用户群小 |
| B | 几乎所有应用：原生 View、Compose、WebView、大部分 Flutter | 无障碍服务读文字节点和坐标，用无障碍悬浮层贴译文，可设成不挡点击 |
| C | 游戏、图片、视频 | MediaProjection 截屏（Android 14 起每次使用都要用户确认）+ ML Kit 端侧 OCR |
| D | 设了禁止截屏的应用（银行等）、带版权保护的视频 | — |

不用 root 也能对大多数应用自动贴译文。限制：Google Play 对无障碍服务的非无障碍用途审核严，可能要在 Play 以外分发；从 Play 以外安装的应用，开启无障碍服务时会被系统"受限设置"拦一下，要用户手动放行。做法：单独的 App，界面和平台层用 Kotlin，Rust 核心通过 Tauri 移动端或 uniffi 复用。

### iOS / iPadOS（远期）：只能做小部分

| 等级 | 覆盖 | 做法 |
|---|---|---|
| A | Safari 网页 | Safari 扩展（与桌面扩展共用代码） |
| C（手动，不能盖在其他应用上） | 截图、选中的文字 | 分享扩展、操作扩展，在随译自己的界面里显示译文 |
| D | 跨应用读取文字、盖在其他应用上、后台实时识别 | 系统不允许 |

只值得做 Safari 扩展加分享扩展。

### 汇总与顺序

| 平台 | 无感（A + B）覆盖面 | 兜底（C） | 主要阻碍 |
|---|---|---|---|
| Windows | 很高 | 完整 | 注入风险、管理员权限的程序 |
| Android（root） | 很高 | 完整 | 用户群小 |
| macOS | 高 | 完整 | 原生程序只能贴译文、需要授权 |
| Android（无 root） | 高 | 每次要确认截屏 | 上架政策 |
| Linux X11 | 中高 | 完整 | 发行版碎片化 |
| Linux Wayland | 中（主要靠 Chromium 系） | 受限 | 协议本身的限制 |
| iOS | 低（只有 Safari） | 只能手动 | 系统封闭 |

推进顺序：

1. Windows 补齐 WebView2 / CEF、浏览器扩展阶段一、UIA 贴译文。
2. macOS。
3. Linux，先 X11 和 KDE。
4. Android（无障碍服务方案）。
5. iOS 的 Safari 扩展和分享扩展。

浏览器扩展做一次，四个桌面浏览器都能用，并直接带上 iOS 的 Safari，性价比最高。

## 多平台打包与发布（2026-11-18）

### 现状：只发 Windows x64 / ARM64

- 发布流程：`.github/workflows/release.yml`。三处版本号（`package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json`）改成一致并提交，推送 `v*` 标签（如 `git tag v0.2.0 && git push origin v0.2.0`），GitHub Actions 会建一个**草稿** Release，上传各架构安装包，确认后在网页上手动发布。在 Actions 页面手动运行则只打包、不建 Release，安装包作为构建产物下载。
- 架构与安装包：

  | 目标 | Rust target | 安装包 |
  |---|---|---|
  | Windows x64 | `x86_64-pc-windows-msvc` | `.msi` + NSIS `.exe` |
  | Windows ARM64 | `aarch64-pc-windows-msvc` | NSIS `.exe`（Tauri 交叉编译 ARM64 只支持 NSIS） |

- 显示名称按系统语言区分（2026-11-18）：`productName` 仍为 `Translate Anything`，NSIS 安装包通过安装钩子 `src-tauri/windows/installer-hooks.nsh` 在中文（简繁）系统上把开始菜单 / 桌面快捷方式改名为「随译」，“设置 → 应用”里的名称也写成「随译」；卸载时一并删除。安装界面语言为简中 + 英文（随系统自动选）。该文件须保存为带 BOM 的 UTF-8。MSI 包的快捷方式暂仍用 `productName`（MSI 面向企业部署，后续如需可用 WiX 片段处理）。
- 便携版（2026-11-18）：每个架构另出 `TranslateAnything_<版本>_<x64|arm64>_portable.zip`，内含 `TranslateAnything\TranslateAnything.exe` 和标记文件 `portable`。程序启动时若自身目录下有 `portable`（或 `portable.txt`）文件，即为便携模式（`config::portable_dir`）：
  - 数据目录（配置、译文库、术语表、沉浸模式参数备份）改为 `<程序目录>\data`，不做 `~/.translate-filter` 旧目录迁移；目录建不出来（如放进了只读位置）就回退到用户目录并打日志。
  - WebView2 缓存改到 `data\webview`（所有建窗口的地方都要调 `PortableWebview::portable_data()`，同一进程必须用同一个缓存目录），否则默认在 `%LOCALAPPDATA%\com.richard.translateanything`。
  - WebView2 运行时用系统自带的（Win10/11 基本都有），不打包固定版运行时（会多约 150MB，不符合体积约定）。
  - 便携模式不提供随译的开机自启动开关。沉浸模式的自动重启沿用运行时检测，不改快捷方式或目标应用的启动项。
- 32 位 Windows（`i686-pc-windows-msvc`）：暂不发布，用户面窄，见下文“32 位”一条。
- 本地打 ARM64：`rustup target add aarch64-pc-windows-msvc`，并在 VS Installer 里给 Build Tools 勾选“MSVC ARM64 生成工具”和“适用于 Windows 的 C++ Clang 编译器”（`rusqlite` 要编译 C 代码；`reqwest` 用的 rustls 底层是 `aws-lc-sys`，编译 ARM64 时只认 `clang-cl`），然后 `pnpm tauri build --target aarch64-pc-windows-msvc --bundles nsis`。CI 的 `windows-latest` 镜像已自带这些工具，工作流里也会先检查 `clang-cl`。本机（2026-11-18）只装了 x64/x86 的 MSVC 工具，ARM64 的编译以 CI 结果为准。
- 版本与更新（2026-11-19，`update.rs`）：设置 → 常规 → “版本与更新”显示当前版本、架构、是否便携版，可手动检查更新、开关自动检查（`config.update.auto_check`，默认开）、跳过某个版本（`update.skip_version`）。检查直接读 GitHub Releases 的 `releases/latest`（草稿和预发布不算），走全局代理；启动 20 秒后检查一次，常驻期间每天一次，发现新版本时托盘菜单多一项“发现新版本”，点开跳到常规页。安装版“下载并安装”下载对应架构的 NSIS 安装包到临时目录、校验大小后启动安装程序并退出本程序；便携版只打开下载页。没用 `tauri-plugin-updater`：它要求发布流程签名并维护 `latest.json`，以后要静默更新再换。
- 代码签名：目前不签名，用户下载后会遇到 SmartScreen 提示。以后买了证书，在 tauri.conf.json 的 `bundle.windows` 里配签名，证书放仓库 Secrets，不进代码。

### 后续：适配 Linux / macOS（未开始，2026-11-18 细化）

**为什么现在不行**：`windows` crate 是无条件依赖，8 个文件直接调 Windows 接口（`ocr` `capture` `input` `dialog` `immersive/procs` `immersive/launch`，以及已带 `cfg` 的 `commands` `i18n`），在其他平台连编译都过不了。另有几处能编译、但行为依赖 Windows 的假设，见下文"隐性差异"。

#### 隐性差异（能编译也要改）

- **坐标系**：后端约定"物理像素、虚拟桌面坐标、左上为原点"。macOS 原生接口用"点"（Retina 下 1 点 = 2 像素），主屏左下为原点，各屏缩放可以不同；Vision 返回 0~1 的归一化坐标、左下为原点。在平台层统一换算成现有约定，上层（`layout` `motion` `live`、前端）不动。
- **透明窗口**：macOS 上 Tauri 透明窗口要在 `tauri.conf.json` 开 `macOSPrivateApi`（用到私有接口，不能上架 Mac App Store，我们也不打算上）；Linux 要桌面开着合成器，否则透明处是黑的。
- **窗口层级**：macOS 的遮罩和翻译框要盖住菜单栏和其他应用的全屏空间，需把窗口层级提到状态栏之上并设 `canJoinAllSpaces | fullScreenAuxiliary`（`objc2` 调 AppKit）；程序设为 `Accessory`，不在程序坞显示图标。
- **托盘**：macOS 在菜单栏，点图标默认弹菜单；Linux（AppIndicator）**收不到图标点击事件**，"左键单击打开设置"无效，只能走菜单项；GNOME 默认不显示托盘图标（Ubuntu 自带扩展，其他发行版要装 AppIndicator 扩展）。
- **字体**：`frame.css` / `overlay.css` 只写了 Windows 字体，要补 macOS（`PingFang SC`、`-apple-system`）和 Linux（`Noto Sans CJK SC`、`WenQuanYi Micro Hei`）的回退；`settings.css` 的等宽字体同理。字号还原的 em 换算系数是在 Windows 字体渲染上校准的，换平台后用 `layout::tests::字号校准` 重新校一遍。
- **"选择程序"**：macOS 选 `.app`（身份校验按 `Contents/MacOS/` 下的实际程序比对），Linux 选可执行文件或 `.desktop`；文件筛选和"程序路径"类文案按平台显示。
- **内嵌浏览器**：macOS 是 WKWebView，Linux 是 WebKitGTK（较慢，翻译框约 30 帧/秒的平移要实测；部分 NVIDIA 驱动需 `WEBKIT_DISABLE_DMABUF_RENDERER=1`）。`PortableWebview` 只在 Windows 生效。
- **便携版**：只在 Windows 提供；macOS 的 `.app` 本身即可拷走，Linux 的 AppImage 近似便携。

#### 沉浸模式在两个平台上

- Electron 通道（CDP + `inject.js`）不依赖截屏和 OCR，原样可用，只需换 `procs` / `launch` 的平台实现——**这是两个平台上最先能交付、也最确定的部分**；Wayland 下悬浮窗受限，沉浸模式不受影响。
- macOS：Electron 应用关掉窗口通常不退出，"等应用完全退出"要提示用户按 ⌘Q。从程序坞、启动台打开无法带参数，所以**无感启动在 macOS 上只做"检测到没带端口就提示一键重启"**，不改写入口。Mac App Store 的沙盒应用可能不允许监听端口，接管不了（遇到再说）。
- Linux：无感启动比 Windows 简单——在 `~/.local/share/applications` 放一份同名 `.desktop` 覆盖系统那份（只在 `Exec` 行追加端口），还原时删掉即可，不碰系统文件，同样记入还原清单。Flatpak / Snap 应用网络默认与主机共享，端口能连，但 `/proc/<pid>/exe` 是沙盒内路径，身份校验要改按沙盒应用 ID 比对。
- XAML / Win32 / DirectWrite 等注入类通道是 Windows 专属。macOS 用辅助功能接口（AX）、Linux 用 AT-SPI 做"贴译文"（通道四），只能读、不能可靠改写；这两种接口都读不到的，走悬浮窗。

#### 需要用户拍板

1. **macOS 签名与公证**（Apple 开发者账号，99 美元/年）。不签名的代价不只是首次打开要"右键 → 打开"：屏幕录制、输入监控等权限是**按签名记的**，未签名（ad-hoc）的程序每次更新后都会被当成新程序，用户得重新授权。
2. **Linux 的 OCR**：
   - Tesseract：作为系统包依赖（`tesseract-ocr` + 语言包），安装包不变大；给词级坐标（`layout.rs` 估字号靠词框）；中文识别一般。
   - PaddleOCR（ONNX，经 `ort` 运行）：中日韩明显更好；模型约 10~15MB + 运行时十几 MB；只给行框，字号估算要另做按行的版本。
   - 只走大模型 VLM：不增体积，但必须配大模型，离线不可用。
   - 倾向：Tesseract 为默认（按发行版依赖安装，不进安装包），VLM 为可选。
3. **Wayland 做到什么程度**：倾向第一版悬浮窗只承诺 X11；Wayland 下沉浸模式照常，悬浮窗只做"截一次、翻一次"的静态模式（portal 截屏；KDE 用 layer-shell 盖回原位，GNOME 只能单独开窗显示译文），不做实时跟随。
4. **测试机**：本机只能保证编译通过（CI 上跑 `cargo check`），截屏、OCR、权限弹窗、窗口层级都必须真机试。macOS 需要一台 Mac（Apple 芯片优先）；Linux 可先用 WSL2（WSLg 是 Wayland + XWayland）或虚拟机。

#### 做法（定下来后按这个顺序）

1. **平台隔离，不改行为**：`windows` 挪到 `[target.'cfg(windows)'.dependencies]`；新建 `platform/` 模块，按能力给出平台无关接口（`ocr::recognize`、`capture::capture_under` / `cursor_state` / `nav_key_down`、`input::start`、`procs::*`、`launch::*`、`os_locale`），Windows 实现搬进 `platform/windows/`，macOS / Linux 先放返回"不支持"的占位；`dialog.rs` 换官方插件。CI 加 `macos-latest`、`ubuntu-22.04` 两个只跑 `cargo check` 和单元测试的任务，防止以后又写进不带 `cfg` 的 Windows 代码。这一步在本机就能做，不依赖上面任何决策。
2. **两个平台先通沉浸模式**：只需 `procs` / `launch` 两块平台代码，加上托盘、设置窗口、字体在各平台过一遍。
3. **macOS 悬浮窗**：ScreenCaptureKit + Vision + 坐标换算 + 窗口层级 + 权限引导（检测到未授权时在设置里说明并一键跳到系统设置对应页）。最低系统版本定 macOS 13（`bundle.macOS.minimumSystemVersion`）；离线翻译只在 macOS 15+ 可选。
4. **Linux X11 悬浮窗**；Wayland 按第 3 条决策做静态模式。
5. **发布**：矩阵加 macOS（`universal-apple-darwin` 出一个 `.dmg`，体积约为单架构两倍但用户不用挑；或 arm64 / x64 各一个）和 Linux（在 `ubuntu-22.04` 上构建，glibc 兼容面广，出 `.deb` + `.AppImage`；需装 `libwebkit2gtk-4.1-dev`、`libayatana-appindicator3-dev` 以及 `xcap` 用到的 xcb / pipewire 开发包）。Release 说明按平台分节，仍是上中文、下英文。

**32 位**：要发的话，在发布矩阵里加 `i686-pc-windows-msvc`（NSIS）。`aws-lc-sys` 编译 32 位需要 NASM（CI 里装一下即可）；另外 Win32 有些接口在 32 位下名字不同（如 `GetWindowLongPtrW` 只有 64 位才有，32 位是 `GetWindowLongW`），要先在本地跑通 `cargo check --target i686-pc-windows-msvc` 再加进矩阵。

## 里程碑建议

1. **M1 跑通链路** ✅：快捷键 → 框选 → 截屏 → OCR → 翻译 → 显示。
2. **M2 沉浸式实时翻译**：原位覆盖、实时刷新、跟随滚动缩放、只翻新内容、鼠标穿透、工具条。
3. **沉浸模式**（与 M2 并行）：译文本地库 ✅、术语表 ✅、Electron/Chromium 通道 ✅（首个适配 reclaude 客户端）；之后按"后续通道"的顺序：WebView2 / CEF → 浏览器扩展 → UIA 贴译文 → XAML → 进程内 hook（按需）。
   - **浏览器扩展**（目标全面超越沉浸式翻译，见"浏览器扩展"一节）：阶段一网页核心体验（段落级双语对照、网站规则、划词、悬停、输入框、AI 上下文翻译，单独使用 / 连接随译两种运行方式，共用核心编译为 WASM）→ 阶段二视频字幕、图片与漫画 → 阶段三文档翻译、会议翻译（桌面端）。
4. **翻译过滤与大模型引擎**（规划中，按顺序）：
   1. `filter.rs`：统一两边规则、用户词表与正则、`whatlang` 语言识别、判断带原因、"引擎原样返回"自动学习；
   2. 引擎列表混排：普通引擎、AI 翻译、离线翻译一个列表，可增删、弹窗添加、按单项冷却；界面"大模型"改称"AI 翻译"；
   3. AI 翻译 Provider：结构化输入输出、`keep` 回写译文库、防注入校验；
   4. 悬浮窗接 VLM（OCR 定位 + 只发未命中的块，单项开启视觉，一次纠错 + 翻译）；
   5. 句内专有名词占位符保护；
   6. 离线翻译：先做 Bergamot 原型测速度、质量、体积 → 接入引擎列表与语言包管理 → "先离线、后替换"两段式返回。
5. **M3 可配置**：配置文件 + 设置界面 + 托盘。
   - 已完成 ✅：沉浸模式应用管理（按应用开关、身份校验、状态、一键以沉浸模式启动/重启、识别 Electron 应用）、译文库查看与改译、术语表、常规设置；
   - 翻译引擎设置界面已有拖动排序 + 启用开关 + 测试；混排列表与添加弹窗见第 4 步；
   - 已支持随译登录后托盘自启动、沉浸模式按应用自动重启。入口参数改写与还原、弹通知提示重启仍属后续方案。过滤原因展示与“改为翻译 / 改为不翻”待做。
6. **语言包模式**（规划中，在占位符保护之后）：首批 JSON（含 ICU）与 gettext 适配器、替换 / 补全 / 新增三种操作、完整性校验拦截、备份还原与更新后自愈；之后 Qt `.qm`、`.properties`、.NET 附属程序集；Electron 运行时语言包需逐个应用实测。
7. **M4 打磨**：多显示器、多浮窗、视觉直译（悬浮窗"识别方式"切换）。
8. **发布**：Windows x64 / ARM64 自动打包 ✅（推 `v*` 标签出草稿 Release）；之后视需要做代码签名、macOS、Linux（见“多平台打包与发布”）。
9. **移动端**（远期）：Android（无障碍服务贴译文 + MediaProjection 截屏 OCR）、iOS（Safari 扩展 + 分享扩展），见"各平台覆盖范围"。
